### Critical findings from code review

- Current vault persistence is path-keyed only: `VAULT_FILES_BY_PATH` and `VAULT_FOLDERS_BY_PATH` with `VaultPath` as the primary key; no ID-keyed primary tables exist yet.
- `vault::storage::Repository` currently exposes path-oriented CRUD/list methods (`get_file`, `get_folder`, `list_files`, `list_folders`) and batch read/write transaction wrappers; new API needs to coexist cleanly or replace these contract points consistently.
- `vault::processor` compare/prune logic depends on full scans (`list_files`, `list_folders`) and exact path lookups (`get_file`, `get_folder`) for freshness detection and deletion; repository signature changes here are high-coupling.
- Markdown routing currently derives note candidates from `VaultFile` path extension checks and path-based note conversion; introducing `FileView`/`DirView` cannot regress this workflow.
- `vault::mod` still exports old path-keyed table definitions and mixed old/new models; storage-table issue is the pivot point for making model migration usable in downstream processor integration.

### Implementation effect analysis (thorough)

- **Data model/storage coupling:** introducing `UuidTable<FileView>` and `UuidTable<DirView>` changes canonical identity from path to ID; path tables become secondary indexes and must not become hidden sources of truth.
- **Index coherence risk:** every write/update/delete must maintain all index surfaces atomically: primary ID table, path index, basename multimap, parent multimap, and format multimap.
- **Rename/move semantics:** path changes should update path/basename/parent indexes without rewriting identity rows; this issue should establish repository primitives that make that behavior possible.
- **Query correctness boundaries:** basename and format multimaps can over-return stale IDs unless delete/update fanout is complete; repository must define behavior for missing/stale index pointers (reject vs heal-on-read).
- **Scan-time performance tradeoff:** processor currently performs full scans and map materialization; adding indexed queries enables targeted reads but can increase write amplification.
- **Transaction shape:** current `with_batch_write` model is a good fit, but multi-index mutations require stricter ordering and rollback guarantees than current two-table writes.
- **Compatibility window:** issue 15 depends on this issue and intends old-table deletion; this issue should preserve a migration-safe bridge (or explicit incompatibility note) so downstream work can flip in one bounded step.
- **Testing surface expansion:** correctness now includes not only CRUD persistence but index referential integrity under insert, update, move/rename, and delete paths.

## Agent Brief (Implementation)

> *This was generated by AI during triage.*

### Outcome

Implement inode-oriented vault storage tables and index-backed repository queries so vault persistence supports stable ID identity plus fast exact/path/basename/parent/format retrieval.

### Current behavior

- Vault entries are stored only by normalized path keys in two tables.
- Repository queries are limited to path lookups and whole-table scans.
- No first-class basename/parent/format indexes are maintained.

### Desired behavior

- File and directory records are persisted in primary ID-keyed tables.
- Path lookups are provided by path->ID index tables.
- Query-oriented multimaps (basename, parent, format) are maintained transactionally.
- Repository API exposes exact lookups, indexed queries, and full scans matching this issue's acceptance criteria.

### Key interfaces

- `Repository` trait (vault storage contract):
  - Exact lookups: `find_file_by_path`, `get_file`, `get_dir`, `get_entry`.
  - Indexed queries: `find_files_by_basename`, `find_files_by_parent`, `list_markdown_files`, `list_files_by_format`.
  - Full scans: `list_all_files`, `list_all_dirs`.
- `RedbRepository` adapter:
  - Must implement all repository methods with consistent transaction and error semantics.
- Table/index definitions:
  - Primary: `UuidTable<FileView>` and `UuidTable<DirView>` keyed by `FileId`/`DirId` UUID bytes.
  - Path index: `NormalizedPath -> FileId`, `NormalizedPath -> DirId`.
  - Multimap index families: basename, parent, format, using `UuidMultimap` where keys/values are UUID-based.

### Acceptance criteria clarifications

- Writes are atomic across primary and all relevant index tables (no partial index updates).
- Delete/update operations remove stale multimap membership for prior values.
- `get_entry` returns typed file/dir entry semantics without ambiguous cross-table collisions.
- `list_markdown_files` derives from format index semantics and is consistent with `list_files_by_format(Markdown)`.
- Batch transaction APIs remain usable by `VaultProcessor` and preserve current error typing boundaries.

### Out of scope

- Deleting legacy `VaultFile`/`VaultFolder` models and old path-keyed tables (handled by issue 15).
- Refactoring vault processor discovery/compare/prune algorithms beyond interface compatibility.
- Cross-context changes outside vault storage and immediate adapters/tests.
