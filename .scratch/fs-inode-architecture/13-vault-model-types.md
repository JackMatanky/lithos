## Triage Review

> *This was generated by AI during triage.*

### Recommendation

- Category: `enhancement`
- State: `ready-for-agent`
- Rationale: this issue is implementable as a bounded domain-model evolution with explicit acceptance criteria and clear integration points in `vault` storage/processor.

### Critical findings from code review

- `vault/model.rs` already defines path+metadata models (`VaultPath`, `VaultFile`, `VaultFolder`) and currently uses path-keyed identity rather than inode identity.
- `vault/storage.rs` persists `VaultFile` and `VaultFolder` in path-keyed tables (`VAULT_FILES_BY_PATH`, `VAULT_FOLDERS_BY_PATH`) and repository APIs are path-centric.
- `vault/processor.rs` scan/compare/prune stages track `HashSet<VaultPath>` and compare entries by path and metadata; markdown routing also starts from path-derived entries.
- `vault/mod.rs` re-exports only current model types (`VaultFile`, `VaultFolder`, `VaultPath`) and declares only path-keyed tables.
- `UuidV7` infrastructure and established ID newtype patterns already exist in the codebase (`utils/uuid.rs`, plus id wrappers in `note`, `schema`, `template`) and should be mirrored for `FileId`/`DirId`.

### Impact / blast-radius assessment

- Overall risk: **HIGH** (cross-cutting identity model shift from path identity to inode-style IDs inside the vault context).
- High-impact areas:
  - `vault/model.rs` (new core types, archived representations, helper APIs)
  - `vault/storage.rs` repository contracts (likely dual path+id lookups or staged migration)
  - `vault/processor.rs` compare/update/prune logic (path set vs id graph semantics)
  - `vault/mod.rs` exports and potentially new table definitions
- Likely secondary impacts:
  - note-routing handoff metadata (`NoteFileInfo` creation paths)
  - tests around scan report counts and update classification
  - serialization compatibility for persisted rkyv data

## Agent Brief (Implementation)

> *This was generated by AI during triage.*

### Outcome

Introduce inode-identity vault model types (`FileId`, `DirId`, views, normalized paths) while preserving vault invariants and providing a safe migration path from path-keyed internals.

### Scope (must do)

1. Add new model types in `vault/model.rs`:
   - `FileId(UuidV7)`, `DirId(UuidV7)` newtypes with ergonomic constructors/accessors and conversion patterns aligned with existing domain IDs.
   - `NormalizedPath` with vault-relative normalization rules (forward slashes, validated construction).
   - `FileView`, `DirView`, `FsEntryView` with required fields/helpers from acceptance criteria.
2. Ensure rkyv support:
   - archive/serialize/deserialize derives and archived compatibility for new types.
3. Update vault module exports:
   - expose new types from `vault/mod.rs`.
4. Integrate without breaking existing behavior:
   - either staged coexistence with `VaultFile`/`VaultFolder` or direct replacement with compatibility layer where needed.
5. Add tests:
   - ID generation/roundtrip semantics.
   - view construction invariants.
   - helper methods (`id_bytes`, `parent_id`, `name`, `is_file`, `is_dir`).
   - normalized path validation/normalization behavior.

### Non-goals

- No full repository schema migration outside what is necessary to satisfy issue acceptance.
- No redesign of note/schema/template contexts.
- No changes to vault scan policy/security validator behavior beyond required path normalization for `NormalizedPath`.

### Constraints

- Preserve vault path safety invariants and deterministic behavior.
- Follow existing `UuidV7` domain newtype conventions in this repository.
- Keep public API behavior explicit and documented; no hidden panics/unwraps in production paths.

### Done when

- All acceptance criteria are complete.
- New model types are exported from `vault/mod.rs`.
- Unit tests cover IDs, views, helper methods, and normalization rules.
- `mise run verify` passes.
