## Agent Brief

> *This was generated by AI during triage.*

### Critical Review and Impact Analysis

This migration is high-leverage and deceptively risky: the mechanical type swap (`FileEntry` -> `FsEntry`) is straightforward, but behavior drift risk is in caller assumptions ("scanner returns only files") and metadata shape assumptions (`FileMetadata` always available without branching).

GitNexus + source audit findings:
- `FileEntry` call sites are concentrated in `fs/scanner`, `fs/reader`, `schema/discovery`, and `config/discovery`; current repository grep shows 40 Rust matches (lower than prior 104 estimate, suggesting prior count was stale or broader scope).
- `DirScanner.entries` upstream impact is currently test-heavy in graph output, but production consumers are visible in schema discovery scan paths; this means compile safety is high, semantic safety still needs explicit tests.
- `Reader.list_entries` currently delegates to `DirScanner.entries` and returns only files; changing this contract can silently affect downstream code that assumes file-only metadata.
- `SchemaDiscovery::scan_filesystem` and `Config::DiscoveryEngine::scan_filesystem` participate in builder/load flows; these are sensitive paths because they gate ingestion.

Key semantic hazards to explicitly guard:
- Directory inclusion where file-only behavior was implicit.
- Filename extraction differences between file and dir variants.
- Metadata handling branch explosion (`FileMetadata` vs `DirMetadata`) that could lead to fallback defaults masking incorrect variant handling.
- API ergonomics regressions causing ad-hoc cloning or repeated pattern matching in callers.

### Agent Brief (Durable, Behavior-First)

**Category:** enhancement

**Summary:** Replace legacy file-only discovery payloads with unified filesystem entry payloads while preserving file-discovery behavior where required.

**Current behavior:**
- Discovery-oriented APIs expose `FileEntry` and therefore imply "file-only" semantics through both type and caller expectations.
- Some discovery components construct `FileEntry` directly rather than consuming typed scanner entries.
- Callers access fields directly (path/filename/metadata) with no variant checks.

**Desired behavior:**
- Discovery APIs that currently emit `FileEntry` emit `FsEntry` (or explicitly file-filtered wrappers) with no ambiguity about variant handling.
- File-only workflows remain file-only by explicit filtering (`is_file`/`as_file`) rather than implicit type constraints.
- Callers have ergonomic, low-friction read access patterns so migration does not encourage repetitive matching, redundant clones, or lossy metadata fallbacks.

**Key interfaces and contracts:**
- `DirScanner::entries(...)` and `FsReader::list_entries(...)` should converge on a unified entry type contract that does not regress ordering guarantees.
- Schema discovery entry separation logic should only process `FsEntry::File` as schema candidates; directory entries must be skipped or rejected deterministically.
- Config discovery for global/vault config should preserve single-file resolution semantics and produce deterministic filename/path metadata behavior.
- `FsEntry` should expose accessor APIs that support migration ergonomics while remaining explicit about variant-dependent metadata.

**Acceptance criteria (expanded):**
- [ ] `DirScanner.entries()` returns `Vec<FsEntry>` and preserves path-sorted output behavior.
- [ ] `FsReader.list_entries()` returns `Vec<FsEntry>` and retains existing glob + ordering semantics.
- [ ] `SchemaDiscovery` and `PropertyBankDiscovery` consume `FsEntry` and process only file variants for schema materialization.
- [ ] `ConfigDiscovery` consumes `FsEntry` (or performs explicit file extraction) without behavior changes to global/vault config resolution precedence.
- [ ] `FsEntry` provides ergonomic accessors needed by migrated callers (including path and metadata access patterns) without forcing direct field-style assumptions.
- [ ] Legacy `FileEntry` type and re-export are fully removed once all call sites compile and pass behavior tests.
- [ ] Full verification via `mise run verify` passes.

**Out of scope:**
- Changing discovery precedence or business rules for config/schema selection.
- Adding new scanner filtering capabilities unrelated to `FileEntry` -> `FsEntry` migration.
- Refactoring unrelated vault ingestion/storage layers beyond what is necessary for type migration.
