## Agent Brief (v2 - 2026-05-27)

> *This was generated by AI during triage.*

**Category:** enhancement
**Summary:** Finalize serialization placement policy and verification.

**Current behavior:**
Serialization placement varies across contexts. Some (like `Schema::save_many_schemas`) serialize inside `Store::write` closures, while others (like `Template::save_many_templates`) pre-serialize outside.

**Desired behavior:**
1. **Define Policy:** Standardize on pre-serialization **outside** `Store::write` closures for both single and batch writes to minimize write-lock duration.
2. **Exception Case:** Serialization may happen inside the closure ONLY if it depends on data generated within the transaction (e.g., auto-incremented versions).
3. **Refactor:** Apply this policy to all context repository adapters (`note`, `schema`, `template`, `config`).
4. **Verify:** Ensure atomicity is preserved and performance is improved or maintained.

**Key interfaces:**
- `ArchivedEntity` (`to_bytes`) - the serialization entry point.
- `Store::write` - the transaction boundary.
- `WriteRepository` implementations in `lithos-core/src/*/storage/write.rs`.

**Acceptance criteria:**
- [ ] Serialization placement policy is documented in `docs/engineering/db/serialization-policy.md`.
- [ ] `RedbRepository` implementations for `note`, `schema`, `template`, and `config` follow the policy.
- [ ] Batch operations (`save_many_*`) use pre-serialization into a `Vec` before opening the transaction.
- [ ] Tests verify that failed serializations (outside OR inside) do not leave partial state.
- [ ] Performance impact is assessed (via benchmarks or reasoning about lock duration).

**Out of scope:**
- Changing the serialization format (`rkyv`).
- Optimizing the serialization process itself.

## Acceptance criteria

- [ ] Policy for serialization placement is documented and approved.
- [ ] Context write adapters align with policy.
- [ ] Final verification confirms no invariant regressions.
