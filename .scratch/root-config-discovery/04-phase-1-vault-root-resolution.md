## Triage Decisions (Approved Defaults)

> *This was generated by AI during triage.*

**Why `VaultRootResolution` needs resolved canonical path payloads:**
- `ConfigLocation` models *config file* location taxonomy, not vault root
  source resolution.
- Phase 1 must resolve root *before* config file discovery; root outcome cannot
  depend on config candidate structures that are produced later.
- Carrying canonical root in `VaultRootResolution` keeps the result
  self-contained for downstream consumers (discovery, diagnostics, repository
  lookup) without re-resolving paths or duplicating state.
- A payload-bearing root outcome reduces drift risk between "source selected"
  and "path actually used"; this is important for symlink/case normalization
  behavior.

**Canonical marker set for ascending discovery (this phase):**
- `lithos.{toml,json,yaml,yml}` at candidate directory root.
- `.lithos.{toml,json,yaml,yml}` at candidate directory root.
- `.lithos/config.{toml,json,yaml,yml}` in candidate directory.

This aligns with the existing local config location taxonomy and avoids
introducing new marker concepts in Phase 1.

**`LITHOS_CEILING_DIRS` parsing strictness:**
- Split on platform path-list separator (`:` on Unix).
- Trim whitespace per segment.
- Ignore empty segments and emit typed warning.
- For non-empty segments: attempt canonicalization.
  - If canonicalization fails or target is not a directory: emit typed warning
    and ignore that segment.
- If all segments are invalid after filtering, treat as "no ceiling set"
  (non-fatal) and continue traversal.

Rationale: strict on valid segments used as boundaries, lenient on malformed
input to avoid hard-failing config load due to operator typos.

## Approved Architecture Update

> *This was generated by AI during triage.*

Use a lean root resolver design that avoids speculative type proliferation and
keeps root resolution cohesive in one file unless clear subgroups emerge.

**File layout:**
- Use `config/discovery/resolver.rs` for the initial root resolution orchestration,
  resolver input/result types, policy, override validation, ceiling parsing,
  marker lookup, and traversal helpers.
- Keep `config/discovery/diagnostics.rs` for typed discovery warnings in the initial implementation.
- Do not split into a `root/` subdirectory unless the file develops clearly
  independent cohesive groups that justify extraction.

**Core types:**
- `RootResolver { policy: RootResolutionPolicy }` owns stable resolver policy.
- `RootResolverInput<'a>` borrows per-call inputs: explicit path, env path,
  CWD, and raw ceiling dirs.
- `RootResolutionResult { root, marker, source, warnings }` is the resolver
  output.
- `RootResolutionSource` records successful provenance:
  `ExplicitFlag`, `EnvironmentVariable`, or `AscendingDiscovery`.
- Do not introduce a separate `RootResolutionOutcome` type for this slice.
- Do not introduce `DiscoveredRootMarker`; reuse `DiscoveredConfigFile` for the
  matched local config marker that establishes the vault root.

**Not-found behavior:**
- Represent not-found as `RootResolutionResult { root: None, source: None, .. }`.
- Not-found is an expected non-fatal discovery state, not an error.
- The discovery orchestrator can later map this contextual state into CLI/user
  diagnostics if needed.

**Marker representation:**
- Use `DiscoveredConfigFile` for root marker matches, not for the root
  directory itself:
  - `base` is the candidate vault root.
  - `path` is the matched marker config file.
  - `location` is `ConfigLocation::Local(...)`.
  - `format` is the matched structured format.
- Reuse `LocalConfigLocation::candidate_path` and
  `StructuredFileFormat::PRECEDENCE` instead of duplicating marker path rules.

**Policy:**
- Keep `RootResolutionPolicy` intentionally small.
- For this slice it should only encode behavior that actually varies, such as
  whether a marker at the ceiling directory is allowed.
- Avoid speculative fields for max depth, symlink policy, or missing behavior
  until a concrete requirement appears.

**Diagnostics:**
- Keep aggregate `DiscoveryWarning` in `diagnostics.rs` using the shape:
  `Local(...)`, `Format(...)`, `CaseCorrection { .. }`, and
  `RootResolution(RootResolutionWarning)`.
- `RootResolver` should return `Vec<RootResolutionWarning>` internally.
- Discovery orchestration should wrap root warnings into aggregate
  `DiscoveryWarning::RootResolution(...)` when composing full discovery output.
- Continue using `thiserror` for typed library errors; do not introduce
  `anyhow`, `miette`, `ariadne`, or `codespan-reporting` for this slice.

**Approved implementation sequence:**
1. RED: adjust/add tests around `RootResolver` and `RootResolverInput` as the
   public internal seam.
2. GREEN: rename/refactor root resolver code into `resolver.rs` with
   `RootResolver { policy }` and borrowed `RootResolverInput<'_>`.
3. RED: test that ascending marker discovery returns a canonical root path and
   `DiscoveredConfigFile` marker containing base/root, marker path, location,
   and format.
4. GREEN: replace boolean marker detection with structured marker lookup.
5. RED: test not-found as `root: None` and `source: None`.
6. GREEN: remove `VaultRootResolution`/`RootResolutionOutcome` style result
   modeling from this slice.
7. RED: test root-resolution warnings remain phase-local and can be wrapped by
   aggregate `DiscoveryWarning`.
8. GREEN: keep `RootResolutionWarning` local to resolver output and
   `DiscoveryWarning::RootResolution(...)` as aggregate diagnostics shape.
9. REFACTOR: move remaining loose helper functions into `impl RootResolver`
   where practical, keeping private free functions only if they are pure,
   standalone helpers with no resolver policy dependency.
10. Verify with `mise run fmt`, `mise run test:unit`, and `mise run lint` if
    feasible.
