## What to build

Add a minimal discovery-focused CLI surface in `lithos-cli` to exercise and verify root/config discovery behavior directly during development.

This slice introduces `config where`, `config list-sources`, and `config check` with deterministic outputs, warning visibility, and scripting-friendly exit semantics.

## Acceptance criteria

- [ ] `lithos config where` reports resolved vault root, discovered config files, source/location metadata, and warnings.
- [ ] `lithos config list-sources` enumerates all candidate paths checked (found/not-found) in deterministic order and always exits 0.
- [ ] `lithos config check` validates discovery outcomes and supports strict warning escalation mode.
- [ ] Flags are wired: `--vault`, `--config`, `--no-global-config`, `--format`, `--verbose`, `--strict`.
- [ ] `--format` supports the PRD formats still intended for this surface: `human`, `json`, and `toml` unless implementation discovers an accepted ADR superseding `toml`.
- [ ] Exit codes are deterministic: `0` success, `1` root-not-found, `2` explicit-path-invalid or strict-warning failure, `3` permission-error.
- [ ] `lithos config list-sources` always exits `0`, including when no vault root is found.
- [ ] `lithos config check --strict` promotes warnings to failure with exit code `2`.
- [ ] Human-readable, JSON, and TOML output modes are supported for discovery commands unless `toml` is explicitly removed by a documented decision.
- [ ] Verbose/trace diagnostics are emitted to stderr while structured output remains stdout-friendly.
- [ ] CLI tests validate command behavior, exit codes, and precedence semantics.
- [ ] CLI handlers do not parse, validate, hash, or merge config file contents for these discovery-only commands.
- [ ] CLI handlers respect ADR 024 by going through an app-level discovery/bootstrap facade rather than importing both Discovery and Config directly.
- [ ] If the existing `Bootstrapper::run()` always builds `Config`, add a separate app-level discovery-only method/facade for these commands instead of calling `run()` and accidentally parsing Config.

## Agent Brief

> *This was generated by AI during triage.*

**Category:** enhancement

**Summary:** Add minimal CLI discovery commands to expose root/config discovery outcomes in real execution.

**Current behavior:**
Discovery behavior is difficult to validate from CLI because dedicated commands
for resolution introspection are not available. Users and developers must infer
root/config resolution from downstream command behavior or logs.

**Desired behavior:**
`config where`, `config list-sources`, and `config check` expose deterministic
discovery outputs, warnings, and exit semantics through an app-level boundary.
These commands must not parse or validate config contents. Structured output
remains stdout-friendly and verbose diagnostics go to stderr.

**Key interfaces:**
- CLI command intents for `where`, `list-sources`, `check`
- App-level discovery/bootstrap facade used by CLI handlers rather than
  importing Discovery and Config directly; use `Bootstrapper::run()` only if it
  can preserve discovery-only behavior for these commands
- Discovery output serialization (`human`, `json`, `toml` unless superseded)
- Exit code taxonomy and strict warning escalation
- Trace stream split: diagnostics to stderr, structured output to stdout

**Acceptance criteria:**
- [ ] Command outputs are deterministic and script-friendly.
- [ ] Exit codes map cleanly to discovery outcomes.
- [ ] `list-sources` always exits `0`; `check --strict` maps warnings to exit `2`.
- [ ] Precedence behavior is externally verifiable via CLI tests.
- [ ] CLI handlers respect the app/discovery/config boundary from ADR 024.
- [ ] Discovery commands do not parse config contents as a side effect.

**Out of scope:**
- Config content parsing/validation
- Indexer integration
- Broader CLI redesign outside discovery commands
- Implementing or exposing deferred trusted-path second-pass discovery
