## What to build

Refactor `lithos-core/src/discovery` into the MVP `DiscoveryService` design from the discovery redesign decisions.

This slice should deliver one complete discovery execution path through the new public API: construct `DiscoveryService`, call `discover(InvocationInput)`, and receive `(DiscoveryResult, DiscoveryReport)` without involving Config or CLI code.

## Acceptance criteria

- [ ] `DiscoveryService` is the public discovery entry point and uses the self-builder pattern (`default()...build()?`).
- [ ] `DiscoveryService` owns stable builder config: global directories, `suppress_global`, marker pattern lists, boundary marker constants, and precedence settings.
- [ ] `InvocationInput` carries only per-call values: `flag_path`, `env_path`, `cwd`, and `ceiling_dirs_raw`.
- [ ] A private `DiscoveryMachine` owns the internal typestate pipeline for the 6-phase discovery process.
- [ ] `DiscoveryMachine` uses the explicit state sequence `Initialized -> Preempted -> Anchored -> Traversed -> GlobalResolved -> Finalized`.
- [ ] Each `DiscoveryMachine` transition is typed so invalid phase ordering is not representable by callers or internal code.
- [ ] `DiscoveryMachine` states use validated `fs` path types after validation/canonicalization: `DirPath` for directories and `FilePath`/`FileNode` for discovered marker files.
- [ ] Raw `&Path` values remain only at input/override boundaries where invalid paths must still be reportable.
- [ ] `DiscoveryService::discover(&self, InvocationInput<'_>) -> Result<(DiscoveryResult, DiscoveryReport), DiscoveryError>` is the single MVP invocation method.
- [ ] No second discovery method for trusted-path/global-config follow-up is added or anticipated in the MVP interface.
- [ ] `DiscoveryResult` replaces the old vault/global split and contains `vault_root`, ordered `vault` markers, and ordered `global` markers using validated FS path types.
- [ ] Discovered marker output carries enough FS metadata (`FileNode` or equivalent `FileMetadata`) so Config does not need to re-prove that marker paths are files.
- [ ] `DiscoveryResult` freezes marker lists as `Box<[DiscoveredMarker]>` or an equivalent immutable boxed slice.
- [ ] `DiscoveryReport` carries non-fatal process metadata: `skipped_override`, `skipped_ceilings`, and `traversal_stop_reason`.
- [ ] `SkippedOverride`, `SkippedOverrideReason::{InvalidPath, NotADirectory}`, `SkippedCeiling`, `SkippedCeilingReason::{EmptySegment, InvalidPath}`, and `TraversalStopReason::{NotStarted, FilesystemRoot, ProjectBoundaryMarker, CeilingEnforced}` are represented explicitly.
- [ ] `override.rs` contains `OverrideResolver` for explicit CLI/env path validation and maps missing/not-directory cases into the designed override errors or skipped-override report data.
- [ ] `FolderProbe` replaces `VaultRootProbe` and `GlobalRootProbe` by accepting marker patterns at construction.
- [ ] `walk.rs` keeps `BoundedAscent` and ceiling parsing responsibility.
- [ ] Marker pattern lists and project boundary marker constants live in `policy.rs`; no separate `DiscoveryPolicy` struct remains.
- [ ] Project boundary markers use probe-then-stop semantics.
- [ ] Inaccessible global directories are skipped with `tracing::warn!`; they do not add a `DiscoveryReport` field.
- [ ] `selector.rs` owns candidate deduplication and ordering, absorbing old `select_markers` behavior from `engine.rs`.
- [ ] `DiscoveryError` transparently wraps `OverrideError`, `TraversalError`, and `GlobalError` with `#[from]` conversions.
- [ ] Error variants include `OverrideError::{Missing, NotADirectory}`, `TraversalError::{AnchorCanonicalize, ReadDirectory}`, and `GlobalError::ReadDirectory` with path/source context.
- [ ] `engine.rs` and `diagnostics.rs` responsibilities are removed or migrated.
- [ ] Unit tests cover explicit override, env override, ascending traversal, global fallback, ceiling diagnostics, and boundary marker stopping.

## Agent Brief

> *This was generated by AI during triage.*

**Category:** enhancement

**Summary:** Replace the current discovery internals with the MVP `DiscoveryService` API and typed discovery pipeline.

**Current behavior:**
Discovery is still shaped around older engine/probe/diagnostic concepts that split vault and global discovery and make downstream consumers understand too much process metadata.

**Desired behavior:**
Discovery exposes one public service API: construct `DiscoveryService`, validate it with `build()`, call `discover(InvocationInput)`, and receive `DiscoveryResult` plus `DiscoveryReport`. `DiscoveryResult` is clean domain data for Config; `DiscoveryReport` is process metadata for Bootstrapper and CLI rendering.

**Key interfaces:**
- `DiscoveryService` — self-builder and public discovery entry point with stable configuration fields.
- `InvocationInput` — per-call input only: explicit paths, current working directory, and raw ceiling data.
- `DiscoveryMachine` — private typestate pipeline with states `Initialized`, `Preempted`, `Anchored`, `Traversed`, `GlobalResolved`, and `Finalized`.
- `DiscoveryService::discover()` — the only MVP invocation method, returning `(DiscoveryResult, DiscoveryReport)`.
- `DiscoveryResult` — optional vault root plus immutable ordered vault/global marker lists using validated FS types.
- `DiscoveryReport` — skipped override, skipped ceilings, and traversal stop metadata with explicit supporting enums.
- `OverrideResolver`, `FolderProbe`, `selector.rs`, `policy.rs`, and layered discovery errors — module responsibilities from the redesign ADR.
- `BoundedAscent` — traversal and ceiling parsing remains in `walk.rs`.

**Acceptance criteria:**
- [ ] `DiscoveryService` is the public discovery entry point and uses the self-builder pattern.
- [ ] `InvocationInput` carries only per-invocation values.
- [ ] The private discovery pipeline follows the six-phase process and returns one `DiscoveryResult` plus one `DiscoveryReport`.
- [ ] No deferred trusted-path second discovery method is introduced in the MVP interface.
- [ ] Discovery output uses validated FS path/file types after validation while preserving raw paths at invalid/reportable input boundaries.
- [ ] Report and error supporting types match the redesign decisions closely enough that callers can distinguish override, traversal, and global-resolution failures.
- [ ] Old `engine.rs` and `diagnostics.rs` responsibilities are removed or migrated into the new service, override, selector, report, and error boundaries.
- [ ] Unit tests cover explicit override, env override, ascending traversal, global fallback, ceiling diagnostics, and boundary marker stopping.

**Out of scope:**
- Config building, parsing, merging, or staleness comparison.
- Bootstrapper orchestration between Discovery and Config.
- CLI discovery subcommands.
- Deferred two-phase discovery through global config trusted paths.

### Rust Best Practices Analysis

The following concerns are flagged **proactively** for the implementing agent. They are not blockers but are likely pitfalls given the scope of this refactor.

#### 1. Typestate pipeline (`DiscoveryMachine`) — Chapter 7

The 6-phase typestate is well-motivated (compile-time phase ordering, zero runtime cost). The ADR references Hoverbear's pattern correctly.

**Watch-outs:**
- Each state struct should hold only the data produced by its phase — don't carry the full previous state. The `Traversed` state should own `vault_root: Option<DirPath>` and `vault_markers: Vec<DiscoveredMarker>`, not a clone of `Anchored`.
- `PhantomData` is zero-size after compilation but adds generic parameters to every `impl` block. With 6 states, this means 5 `From` implementations and 6 `impl` blocks. Keep each phase method small and delegate to helper functions in the same file to avoid the "verbose state machine" anti-pattern from §7.5.
- The issue correctly says transitions are `impl From<Previous> for Next`. Confirm each `From` is infallible — errors must be surfaced *before* the transition, not inside it. Phase 2 (Preempted) returns `Result` at the `discover()` call site; the typestate itself should not hold `Result`.

#### 2. Error hierarchy — Chapter 4

The issue correctly specifies layered `thiserror` errors with `#[from]`:

```rust
#[derive(Debug, thiserror::Error)]
pub enum DiscoveryError {
    #[error(transparent)]
    Override(#[from] OverrideError),
    #[error(transparent)]
    Traversal(#[from] TraversalError),
    #[error(transparent)]
    GlobalResolution(#[from] GlobalError),
}
```

**Watch-outs:**
- Current `error.rs` has a flat 6-variant enum. The agent must delete all 6 existing variants; partial migration risks leaving dead variants behind.
- `OverrideError` has two variants (`Missing`, `NotADirectory`) that map to `SkippedOverride` on the non-fatal path *and* to `OverrideError` on the fatal path. The distinction: if `strict_overrides` (or equivalent) is true, it becomes a fatal `DiscoveryError::Override`; if false, it becomes a `SkippedOverride` on the report. The agent must decide whether `OverrideResolver::resolve()` returns `Result<Option<DirPath>, OverrideError>` and the caller decides, or whether the resolver already makes the fatal/non-fatal call. The redesign decisions document does not specify this explicitly — the agent should follow the pattern where `OverrideResolver` always returns the validation outcome and `DiscoveryMachine` maps it to report vs. error based on policy.
- Do not use `unwrap()` or `expect()` anywhere outside test code. The current `engine.rs` uses `VaultRootProbe.probe(&root)?.unwrap_or_default()` — this pattern is fine (`unwrap_or_default` is not `unwrap`), but the agent should prefer `unwrap_or_default()` over `.unwrap_or(vec![])` throughout.

#### 3. Borrowing and lifetime management — Chapter 1

`InvocationInput<'a>` holds `Option<&'a Path>` and `Option<&'a OsStr>`. This is correct. However:

- `DiscoveryMachine` states that store *validated* paths must own them (`DirPath`, `FilePath`) — they cannot borrow from `InvocationInput` after the input is consumed in phase 1/2. Make sure the typestate design does not attempt to store `&'a Path` inside state structs past the point where validation produces an owned type.
- `FolderProbe` should accept `&[MarkerPattern]` at construction (borrowed from `policy.rs` constants), not an owned `Vec<MarkerPattern>`. The current `VaultRootProbe` and `GlobalRootProbe` are zero-size structs that reference static arrays; `FolderProbe` should do the same (store `&'static [MarkerPattern]` or a `PhantomData` approach).

#### 4. `Box<[DiscoveredMarker]>` vs `Vec<DiscoveredMarker>` — Chapter 3

The issue requires `Box<[DiscoveredMarker]>` for frozen marker lists. This is intentional and correct — it signals that the list is built once and then immutable, and it drops excess Vec capacity.

**Watch-out:** Use `.into_boxed_slice()` on a `Vec<DiscoveredMarker>` at the point of finalization. Do NOT prematurely collect into a boxed slice during the traversal phase where the list is still being built.

#### 5. `walk.rs` migration — ceiling parsing return type

`DiscoveryBoundaries::parse_ceilings` currently takes `&mut Vec<VaultDiscoveryWarning>`. Under the new design it must return `(HashSet<PathBuf>, Vec<SkippedCeiling>)` or similar. The existing `BoundedAscent` iterator signature is clean and should be kept. The function signature change in `parse_ceilings` is a breaking internal API change — the agent must update all call sites in the same PR.

**Watch-out:** `parse_ceilings` currently uses `env::split_paths` + lazy `filter_map` with an `&mut Vec` side channel. Prefer returning `(HashSet<PathBuf>, Box<[SkippedCeiling]>)` where the skipped list is frozen at parse time, consistent with the `Box<[_]>` immutability pattern used elsewhere in this redesign.

#### 6. `#[allow(dead_code, reason = "...")]` annotations

Every non-test symbol in the current discovery module carries `#[allow(dead_code, reason = "Phase-N seam; wired in once orchestration lands")]`. After this refactor, all these annotations must be removed. Leaving stale `allow(dead_code)` annotations is an anti-pattern — clippy will not warn about unused code even if the new seam is broken.

**Suggested approach:** remove all `#[allow(dead_code)]` attributes from the discovery module as a first step. Let the compiler errors guide which old symbols must be deleted vs. migrated.

#### 7. Iterator style — Chapter 1.5

`selector.rs::select_candidate` uses `.iter().min_by(...)` — this is idiomatic and correct. The `select_markers` deduplication that migrates from `engine.rs` currently uses a manual `for` loop over a `Vec` with `.iter().any(...)` for uniqueness checking. This is O(n²). The agent should replace it with a `HashSet<PathBuf>` for seen-path tracking during deduplication, consistent with how `BoundedAscent` uses `HashSet<PathBuf>` for ceilings.

#### 8. Test migration

The issue requires tests for: explicit override, env override, ascending traversal, global fallback, ceiling diagnostics, boundary marker stopping.

The existing `engine.rs` tests (lines 389–1239) cover most of these paths. The agent should:
1. Port the relevant test cases to the new API (`DiscoveryService::discover(InvocationInput)`) rather than rewriting from scratch.
2. Add new tests for the boundary marker stopping behavior (currently untested — `DiscoveryEngine` doesn't implement project boundary markers like `.git`).
3. Add new tests for `SkippedOverride` and `SkippedCeiling` report fields.
4. Test names should follow the descriptive convention: `discover_should_return_skipped_override_when_flag_path_is_missing()`.
