## What to build

Clean up the technical debt in the new top-level `discovery/` context and integrate it into the `config/` orchestration layer.

This slice bridges the gap between the moved path-discovery logic and the legacy `DiscoveryEngine`. It exports the necessary constants, splits the resolver into cohesive modules, and refactors `config/discovery.rs` to consume the new pipeline.

## Acceptance criteria

- [ ] **Discovery Refactor**:
    - [ ] Extract `RootResolutionError` to `discovery/error.rs` and rename to `DiscoveryError` (or similar expressive name).
    - [ ] Split `discovery/resolver.rs` into a directory module (`discovery/resolver/mod.rs`, etc.) to improve maintainability.
    - [ ] Move `LocalDiscoveryWarning` and `FormatDiscoveryWarning` out of `discovery/diagnostics.rs` into a new `config/diagnostics.rs` (classification is a Config concern).
    - [ ] Export `MARKER_FILENAMES` (or similar) as a public constant in `discovery/`.
- [ ] **Config Integration**:
    - [ ] Refactor `config/discovery.rs` (`DiscoveryEngine`) to call `discovery::RootResolver`.
    - [ ] Implement the mapping logic from `discovery::FoundRootMarker` to `config::DiscoveredConfigFile`.
    - [ ] **Delete** the legacy raw scanning methods (`find_global_config`, `find_vault_config`) and legacy result structs (`GlobalDiscovery`, `VaultDiscovery`) in `config/discovery.rs`.
- [ ] **Polish**:
    - [ ] Apply `tracing` spans to the root resolution search and source precedence logic.
    - [ ] Audit visibility (`pub` vs `pub(crate)`) to ensure the Discovery API surface is minimal.
- [ ] **Verification**:
    - [ ] All existing tests in `discovery/` and `config/` pass.
    - [ ] `DiscoveryEngine` integration test verifies it now uses the new resolver.
