# Template Repository Traits

Status: ready-for-agent

## Parent

`.scratch/template-foundation/PRD.md`

## What to build

Define the Template repository port: segregated `ReadRepository`, `WriteRepository`, and unified `Repository` traits following the exact pattern established by the note and schema contexts.

The traits cover:
- CRUD operations for `Template` (find by id, find by path/name, save, delete)
- CRUD operations for `RawTemplateView` (find by path, save, delete)
- Batch raw-view operations for efficient multi-path discovery and atomic cache updates

No filesystem materialization belongs here — the traits are pure persistence ports. No implementation (redb adapter) is required in this slice; the traits and a test-double/in-memory implementation for use in other slices' tests are sufficient.

## Acceptance criteria

- [ ] `ReadRepository` trait defined with at minimum: find `Template` by `TemplateId`, find `Template` by `TemplateName`, list all `Template`s, find `RawTemplateView` by `PathKey`, batch find `RawTemplateView` by a set of `PathKey`s
- [ ] `WriteRepository` trait defined with at minimum: save `Template`, delete `Template` by `TemplateId`, save `RawTemplateView`, delete `RawTemplateView` by `PathKey`, batch save `RawTemplateView`s
- [ ] `Repository` is a unified blanket marker trait: `impl<T: ReadRepository + WriteRepository> Repository for T {}`
- [ ] No filesystem I/O or MiniJinja types appear in any trait method signature
- [ ] An in-memory test implementation is provided (or a testing module following `schema/storage/testing.rs` pattern) so downstream slices can write unit tests without a real redb adapter
- [ ] Repository contract tests cover: save and find round-trip for `Template`, missing-entity behavior (returns `None` or appropriate error), `RawTemplateView` save/find/delete, batch raw-view operations, find-by-name and find-by-id correctness

## Enhanced Triage — Codebase Analysis (2026-06-12)

**Pattern alignment verified against 3 context repositories (schema, note, vault):**

### Repository Structure

All three contexts follow the same structure — `repository.rs` in the context root, `storage/testing.rs` for test doubles. Template should follow suit:

```
lithos-core/src/template/
├── repository.rs      ← CREATE: ReadRepository + WriteRepository + Repository blanket
├── storage/
│   └── testing.rs     ← CREATE: InMemoryRepository (test double)
```

### Method Naming Consistency

The issue's proposed names largely match project conventions (`docs/naming-taxonomy.md`), but **two naming mismatches** exist:

| Proposed Name | Naming Taxonomy Rule | Suggested Fix |
|---|---|---|
| `save_raw_template_views` | Batch ops use `_many` suffix: `save_many_schemas`, `save_many_base_schemas` | Rename to `save_many_raw_template_views` |
| `delete_raw_template_view` | Singular delete is fine (matches `delete_schema`). ✅ | Keep as-is |

All other names align: `find_*` for optional (returns `Option`), `save_*` for upsert, `delete_*` for removal.

### Error Type Design

The issue proposes `TemplateRepositoryError` with `NotFound` / `Serialization` / `Storage` variants. Cross-context analysis:

| Context | Error Type | Variants |
|---|---|---|
| Schema | `SchemaRepositoryError` | `Storage(DbError)`, `Domain(SchemaError)`, `NotFoundById`, `NotFoundByName`, `NotFoundByPath`, etc. |
| Note | `NoteRepositoryError` | `Storage(DbError)`, `DuplicatePath(NotePath)` |
| Vault | `VaultRepositoryError` | `Storage(DbError)` |

**Recommendation**: Keep `TemplateRepositoryError` simple — `Storage(DbError)` + `NotFoundById(TemplateId)` + `NotFoundByPath(PathKey)`. No separate `Serialization` variant — `DbError::Serialization(String)` already exists at `db/error.rs:47` and any serialization failure is wrapped transitively via `Storage(DbError::Serialization(...))`. Mark `#[non_exhaustive]`. Use `thiserror::Error`. Follow the `SchemaRepositoryError` pattern: `Storage` is the only infra variant; context-specific not-found variants carry the identifier for error reporting.

### In-Memory Test Double

The issue says "follow the `schema/storage/testing.rs` pattern". Key details from that pattern:

1. **Uses `db::testing` primitives**: `InMemoryHarness`, `read_lock`, `write_lock`, `FailurePoint`, `FailureInjector`, `InMemoryDbError`
2. **Module gating**: `#![cfg(any(test, feature = "testing"))]` — both `#[cfg(test)]` and bench/feature use
3. **Thread safety**: All maps behind `Arc<RwLock<HashMap<K, V>>>` — `Clone` is cheap (Arc bump)
4. **Failure injection**: Each method calls `self.harness.fail_at(FailurePoint::BeforeRead|BeforeWrite)?` — templated repo must do the same
5. **Helper methods**: `schema_count()`, `clear()`, `harness()` for test assertions
6. **Doc comments required**: Module doc explains "why in-memory repo exists" and "when to use / not use it" (enforced by `missing_docs = "deny"`)

### Contract Tests

The schema context puts contract tests in `lithos-core/tests/schema_storage.rs` — integration tests that exercise `InMemoryRepository` + `RedbRepository` against the same contract. Template should follow the same dual-implementation test pattern, testing both `InMemoryRepository` and (when built) the redb adapter against a shared contract suite.

### Visibility

- `repository.rs` traits: `pub` (used across contexts — template processor, service)
- `storage/testing.rs` `InMemoryRepository`: `pub(crate)` (only used within `lithos-core`)
- Constructor `InMemoryRepository::new()`: `pub(crate)` to be used by downstream module tests

### Project Constraints from lib.rs

- `unsafe_code = "forbid"` — no unsafe blocks
- `unwrap_used` / `expect_used` denied — use `?` and `match`
- `missing_docs = "deny"` — all `pub` items need doc comments

No downstream consumers yet — this is a greenfield port. LOW risk. The traits will be consumed by:
- Template processor (issue 04)
- Template service (issue 05)
- Integration tests in `lithos-core/tests/template_storage.rs`

## Agent Brief

**Category:** enhancement
**Summary:** Define segregated `ReadRepository`, `WriteRepository`, and `Repository` traits for the template context, plus an in-memory test double

**Current behavior:**
No template persistence port exists. Downstream slices (processor, service) have no trait to program against and no test double to use in unit tests.

**Desired behavior:**
A `lithos-core/src/template/repository.rs` module (mirroring `schema/repository.rs`) defines:

- `ReadRepository` trait with at minimum:
  - `find_template_by_id(&self, id: TemplateId) -> Result<Option<Template>, TemplateRepositoryError>`
  - `find_template_by_name(&self, name: &TemplateName) -> Result<Option<Template>, TemplateRepositoryError>`
  - `list_templates(&self) -> Result<Vec<Template>, TemplateRepositoryError>`
  - `find_raw_template_view(&self, path: &PathKey) -> Result<Option<RawTemplateView>, TemplateRepositoryError>`
  - `find_raw_template_views_by_paths(&self, paths: &[PathKey]) -> Result<Vec<Option<RawTemplateView>>, TemplateRepositoryError>`

- `WriteRepository` trait with at minimum:
  - `save_template(&self, template: &Template) -> Result<(), TemplateRepositoryError>`
  - `delete_template(&self, id: TemplateId) -> Result<(), TemplateRepositoryError>`
  - `save_raw_template_view(&self, view: &RawTemplateView) -> Result<(), TemplateRepositoryError>`
  - `delete_raw_template_view(&self, path: &PathKey) -> Result<(), TemplateRepositoryError>`
  - `save_many_raw_template_views(&self, views: &[RawTemplateView]) -> Result<(), TemplateRepositoryError>`  ⚠️ renamed from `save_raw_template_views` per naming taxonomy

- `Repository` as a unified blanket marker: `impl<T: ReadRepository + WriteRepository> Repository for T {}`

- `TemplateRepositoryError` error type covering at minimum: `Storage(DbError)`, `NotFoundById(TemplateId)`, `NotFoundByPath(PathKey)`. No standalone `Serialization` variant — `DbError::Serialization(String)` already exists and is wrapped transitively via `Storage(DbError::Serialization(...))`. Mark `#[non_exhaustive]`.

- An in-memory test double at `lithos-core/src/template/storage/testing.rs` (mirroring `schema/storage/testing.rs`) usable in unit tests for the processor and service slices. Uses `db::testing::InMemoryHarness` + `read_lock`/`write_lock` + `FailurePoint` — feature-gated `#![cfg(any(test, feature = "testing"))]`.

**Key interfaces:**
- `ReadRepository`, `WriteRepository`, `Repository` — pure trait definitions; no filesystem I/O, no `minijinja` types, no `std::fs`
- `TemplateRepositoryError` — new error enum; at minimum `Storage(DbError)`, `NotFoundById(TemplateId)`, `NotFoundByPath(PathKey)`; no standalone `Serialization` variant (covered by `DbError::Serialization` via `Storage`); `#[non_exhaustive]`; implements `std::error::Error` via `thiserror`
- `InMemoryRepository` (test double) — `Arc<RwLock<HashMap>>`-backed; implements both `ReadRepository` and `WriteRepository`; uses `db::testing::InMemoryHarness` for failure injection; lives in `storage/testing.rs` with `#![cfg(any(test, feature = "testing"))]` gating
- Method signatures mirror the schema repository pattern (qualified names like `find_template_by_id`) per schema convention
- `pub` visibility for `ReadRepository`/`WriteRepository`/`Repository` traits; `pub(crate)` for `InMemoryRepository`
- All `pub` items require doc comments (`missing_docs = "deny"`)
- No `unwrap()`/`expect()` in production code (`unwrap_used`/`expect_used` denied)
