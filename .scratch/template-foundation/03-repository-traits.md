# Template Repository Traits

Status: ready-for-agent

## Parent

`.scratch/template-foundation/PRD.md`

## What to build

Define the Template repository port: segregated `ReadRepository`, `WriteRepository`, and unified `Repository` traits following the exact pattern established by the note and schema contexts.

The traits cover:
- CRUD operations for `Template` (find by id, find by path/name, save, delete)
- CRUD operations for `RawTemplateView` (find by path, save, delete)
- Batch raw-view operations for efficient multi-path discovery and atomic cache updates

No filesystem materialization belongs here — the traits are pure persistence ports. No implementation (redb adapter) is required in this slice; the traits and a test-double/in-memory implementation for use in other slices' tests are sufficient.

## Acceptance criteria

- [ ] `ReadRepository` trait defined with at minimum: find `Template` by `TemplateId`, find `Template` by `TemplateName`, list all `Template`s, find `RawTemplateView` by `PathKey`, batch find `RawTemplateView` by a set of `PathKey`s
- [ ] `WriteRepository` trait defined with at minimum: save `Template`, delete `Template` by `TemplateId`, save `RawTemplateView`, delete `RawTemplateView` by `PathKey`, batch save `RawTemplateView`s
- [ ] `Repository` is a unified blanket marker trait: `impl<T: ReadRepository + WriteRepository> Repository for T {}`
- [ ] No filesystem I/O or MiniJinja types appear in any trait method signature
- [ ] An in-memory test implementation is provided (or a testing module following `schema/storage/testing.rs` pattern) so downstream slices can write unit tests without a real redb adapter
- [ ] Repository contract tests cover: save and find round-trip for `Template`, missing-entity behavior (returns `None` or appropriate error), `RawTemplateView` save/find/delete, batch raw-view operations, find-by-name and find-by-id correctness

### Method Naming Consistency

The issue's proposed names largely match project conventions (`docs/naming-taxonomy.md`), but **two naming mismatches** exist:

| Proposed Name | Naming Taxonomy Rule | Suggested Fix |
|---|---|---|
| `save_raw_template_views` | Batch ops use `_many` suffix: `save_many_schemas`, `save_many_base_schemas` | Rename to `save_many_raw_template_views` |
| `delete_raw_template_view` | Singular delete is fine (matches `delete_schema`). ✅ | Keep as-is |

All other names align: `find_*` for optional (returns `Option`), `save_*` for upsert, `delete_*` for removal.

### Error Type Design

The issue proposes `TemplateRepositoryError` with `NotFound` / `Serialization` / `Storage` variants. Cross-context analysis:

| Context | Error Type | Variants |
|---|---|---|
| Schema | `SchemaRepositoryError` | `Storage(DbError)`, `Domain(SchemaError)`, `NotFoundById`, `NotFoundByName`, `NotFoundByPath`, etc. |
| Note | `NoteRepositoryError` | `Storage(DbError)`, `DuplicatePath(NotePath)` |
| Vault | `VaultRepositoryError` | `Storage(DbError)` |

**Recommendation**: Keep `TemplateRepositoryError` simple — `Storage(DbError)` + `NotFoundById(TemplateId)` + `NotFoundByPath(PathKey)`. No separate `Serialization` variant — `DbError::Serialization(String)` already exists at `db/error.rs:47` and any serialization failure is wrapped transitively via `Storage(DbError::Serialization(...))`. Mark `#[non_exhaustive]`. Use `thiserror::Error`. Follow the `SchemaRepositoryError` pattern: `Storage` is the only infra variant; context-specific not-found variants carry the identifier for error reporting.

### In-Memory Test Double

The issue says "follow the `schema/storage/testing.rs` pattern". Key details from that pattern:

1. **Uses `db::testing` primitives**: `InMemoryHarness`, `read_lock`, `write_lock`, `FailurePoint`, `FailureInjector`, `InMemoryDbError`
2. **Module gating**: `#![cfg(any(test, feature = "testing"))]` — both `#[cfg(test)]` and bench/feature use
3. **Thread safety**: All maps behind `Arc<RwLock<HashMap<K, V>>>` — `Clone` is cheap (Arc bump)
4. **Failure injection**: Each method calls `self.harness.fail_at(FailurePoint::BeforeRead|BeforeWrite)?` — templated repo must do the same
5. **Helper methods**: `schema_count()`, `clear()`, `harness()` for test assertions
6. **Doc comments required**: Module doc explains "why in-memory repo exists" and "when to use / not use it" (enforced by `missing_docs = "deny"`)

### Contract Tests

The schema context puts contract tests in `lithos-core/tests/schema_storage.rs` — integration tests that exercise `InMemoryRepository` + `RedbRepository` against the same contract. Template should follow the same dual-implementation test pattern, testing both `InMemoryRepository` and (when built) the redb adapter against a shared contract suite.
