### New finding this pass (BOTH prior passes missed)

#### R20 (P2, latent correctness — soft-fail / detect_deletions coupling)

**Files**: `service.rs:84–105` (soft-fail loop + `detect_deletions` call).

When a per-entry classification error is soft-failed (`Err(IndexerError::Path(e))`,
`service.rs:94–99`), the loop records the failure and `continue`s **without inserting
the entry's path into `ctx.seen_paths`**. `detect_deletions` (`service.rs:105`) then
treats every persisted path not in `seen_paths` as deleted and the run **deletes it
from the repo** (`service.rs:108`).

So the invariant "a soft-failed entry must not cause its own prior record to be
deleted" holds **today only by accident**: the *only* recoverable error
(`IndexerError::Path`) comes from `as_key`/`from_rooted_path`
(`fs/path.rs:999–1013`), which fails on (a) `PathOutsideVaultRootBoundary` — the node
has no vault-relative `PathKey`, so no stored record can match — or (b) `InvalidUtf8`
— likewise no computable `PathKey`. Both failure modes *preclude* a colliding stored
key, so no good record is deletable **right now**.

This is a **fragile, undocumented coupling**, not a present-day data-loss bug. The
moment either (i) a new recoverable `IndexerError::Path`-class error arises whose
path *is* vault-relative-and-already-stored, or (ii) `into_indexed` (which CAN touch
a stored path) is ever folded into the soft-fail set, a transient per-entry failure
will silently delete the previously-good record. The soft-fail design and the
deletion-detection design were each reviewed in isolation; their interaction was not.

**Classification**: Behavioural-guard (RED→GREEN is a *characterization + guard*
test; minimal GREEN is a one-line guarantee, not a logic change today). **Decision
needed from user**: (A) add `seen_paths.insert(entry_path)` on soft-fail so a failed
entry is never considered "absent" (preserves the prior record across a transient
failure — recommended; matches "scan as much as possible"); or (B) leave behaviour
as-is and only add a regression test + a `// ponytail:`-style comment naming the
coupling and the upgrade path. Either way the slice begins with the failing
characterization test below.

#### Slice 2.1 — Soft-fail vs deletion coupling (R20) — DECISION GATE

- **Shape**: Behavioural-guard. **Blocking pre-req**: user picks option **A**
  (insert soft-failed path into `seen_paths`) or **B** (test + comment only). Do not
  start until decided.
- **RED** — `soft_failed_entry_does_not_delete_its_existing_record`:
  - Seed the repo with a valid record at vault-relative path `P` (so `all_paths`
    returns `P`).
  - Drive a run whose scan yields one entry for `P` that soft-fails classification
    **and** one unrelated valid entry. (Constructing a per-entry `Path` failure for a
    path that is *also* a stored `PathKey` is currently impossible by construction —
    see R20 — so this test will require a seam: e.g. a test-only classifier hook, or
    promote the characterization to the `IndexCollector` level by asserting that a
    recorded failure path is added to `seen_paths`.)

    `Some` AND `report.deleted_count() == 0` AND `report.failures().len() == 1`.
  - Under current behaviour this **fails** (P absent from `seen_paths` → P deleted).
- **GREEN (option A)** — in the soft-fail arm (`service.rs:94–99`) insert the entry's
  path key into `ctx.seen_paths` before `continue` (compute the key best-effort; if
  the key is uncomputable the deletion risk does not exist, so guard accordingly).
  Add a `// ponytail:`-style comment naming the coupling.
- **GREEN (option B)** — keep behaviour; the test becomes a *documented expectation*
  of current limits + a comment at `service.rs:94` naming the invariant ("only safe
  because the sole recoverable error precludes a stored key") and the upgrade path.
- **Verify**: per-slice gate.
- **Commit (A)**: `fix(indexer): keep soft-failed entries out of deletion detection`
