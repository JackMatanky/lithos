## What to build

Merge the isolated configuration and discovery mechanisms into a single, cohesive Settings adapter.

1. Create a new crate: `crates/settings` (Package name: `trace-settings`).
2. Move the contents of `crates/config` and `crates/discovery` (which now includes `dirs.rs` and `env.rs`) into this unified `trace-settings` crate.
3. Update `trace-settings` internal modules to expose the necessary APIs.
4. Update every dependent crate to use `trace-settings` instead of the separate config/discovery crates — `trace-note`, `trace-schema`, `trace-template`, `trace-vault`, `trace-app`, and `trace-cli` — plus the root workspace `Cargo.toml` dependency table. This is a workspace-wide `trace_config`/`trace_discovery` → `trace_settings` import rewrite, not just a `trace-app` change.
5. Update `crates/settings/tests/architecture.rs` to ensure any internal module boundaries between the config parser and the discovery engine are maintained.
6. Delete the old `crates/config` and `crates/discovery` folders.

## Acceptance criteria

- [ ] `crates/settings` exists and contains the logic for config, discovery, dirs, and env.
- [ ] The old `config` and `discovery` crates are deleted.
- [ ] `trace-app` successfully orchestrates application workflows using `trace-settings`.
- [ ] The workspace compiles and all tests pass.

## Agent Brief

**Category:** enhancement
**Summary:** Merge the `trace-config` and `trace-discovery` crates into one cohesive `trace-settings` crate, and repoint every workspace dependent at it.

**Current behavior:**
Configuration and discovery are two separate workspace crates (created in the 01-extract-core-contexts slice, which is done):
- `trace-discovery` (`crates/discovery`) owns pre-config filesystem discovery — vault root, root marker, cache root, env reads (`dirs`, `env` modules). Depends only on `trace-fs`.
- `trace-config` (`crates/config`) owns parse/validate/precedence-merge/persist of configuration, and depends on `trace-discovery` in a strict one-way flow: `Config` consumes `DiscoveryResult`; discovery never imports config.
Today that one-way relationship is guaranteed by the compiler (separate crates) plus architecture tests that currently live in the `trace-app` test suite. The settings lifecycle is split across two crates by a boundary that no longer needs to be a crate boundary.

**Desired behavior:**
A single `trace-settings` crate (`crates/settings`, package `trace-settings`) houses the whole inbound settings lifecycle: discovery (vault root, paths, env, cache root) and configuration (parse, validate, merge, persist). The two concerns become internal modules of one crate, with the config→discovery one-way dependency preserved as an *intra-crate* module boundary enforced by architecture tests (the compiler no longer enforces it). Every crate that depended on `trace-config` and/or `trace-discovery` depends on `trace-settings` instead, and the old crates are removed.

**Key interfaces:**
- `trace-settings` crate root — must cohesively re-export both the discovery boundary API (`DiscoveryService`, `DiscoveryResult`, `DiscoveryReport`, `CacheRoot`/`CacheLocation`, `DiscoveryError`, `EnvVars`, `DiscoveryContext`/`DiscoveryEnv`/`DiscoveryFlags`) and the configuration API (`Config`, `Builder`, `Repository`/`ReadRepository`/`WriteRepository`, `RedbRepository`/`RedbStorage`, config error/event types). Keep `config` and `discovery` as distinct internal modules.
- Internal boundary — the `discovery` module must not import the `config` module; the config builder must consume discovery only via `discovery::service::DiscoveryResult` (never discovery internals: policy/engine/diagnostics/source-identity).
- `crates/settings/tests/architecture.rs` — relocate the config↔discovery boundary tests from the `trace-app` suite and rewrite their path globs to the merged crate's internal modules. Carry over (by intent): config-must-not-import-discovery-diagnostics-or-source-identity, config-must-not-own-candidate/location modules, builder-must-not-hardcode-global-config-path, builder-must-not-use-known-vault-root-shortcut, builder-imports-only-`DiscoveryResult`-from-`discovery::service`.
- `testing` feature — currently on `trace-config` (forwards to `trace-db/testing`, exposes an in-memory repository). It must survive on `trace-settings`, since `trace-cli`, `trace-app`, and `trace-template` enable `trace-*/testing`.
- Dependents to repoint (Cargo.toml + `use trace_config::`/`use trace_discovery::` → `use trace_settings::`): `trace-note`, `trace-schema`, `trace-template`, `trace-vault`, `trace-app`, `trace-cli`, plus the root workspace `Cargo.toml` dependency table. (`trace-app`'s bootstrap is the primary consumer, but not the only one.)
- Preserve the crate-level `#![feature(trivial_bounds)]` that both source crates carry.

**Acceptance criteria:**
- [ ] `crates/settings` exists as package `trace-settings`, containing config, discovery, `dirs`, and `env` logic (plus the config `vault`/storage submodules), exposing both discovery results and the configuration API from one crate root.
- [ ] `crates/config` and `crates/discovery` are deleted; the root workspace `Cargo.toml` lists `trace-settings` in place of `trace-config`/`trace-discovery`.
- [ ] Every former dependent (`trace-note`, `trace-schema`, `trace-template`, `trace-vault`, `trace-app`, `trace-cli`) builds against `trace-settings`; no `trace-config`/`trace_config` or `trace-discovery`/`trace_discovery` references remain in the workspace.
- [ ] `crates/settings/tests/architecture.rs` enforces the intra-crate config→discovery one-way boundary, and those tests no longer live in the `trace-app` suite.
- [ ] The `testing` feature is preserved on `trace-settings` and every crate enabling it still compiles.
- [ ] `crates/settings/CONTEXT.md` exists (merging the config + discovery context docs) so the `CONTEXT-MAP.md` Settings link resolves.
- [ ] `cargo check` and `cargo test` pass for the whole workspace.

**Out of scope:**
- Changing configuration formats, precedence rules, or adding new settings.
- The global "Lithos" → "Trace" text/env-var rename — that's 04-global-rename (blocked by this slice). Leave existing `lithos`/`LITHOS` strings, including the `/etc/lithos` assertion in the moved architecture test, untouched here.
- The separate `trace-vault` crate's own responsibilities — it's touched only as a `trace-config` dependent. `trace-config::vault` (a config submodule) and `crates/vault` (`trace-vault` domain crate) are different things; do not fold `trace-vault` into settings.
- `crates/schema`'s internal `discovery` module and its own `DiscoveryResult` — unrelated to `trace-discovery`; do not touch.
