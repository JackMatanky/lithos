# Issue 07: Note context hard cut from private RelativePath to PathKey

Labels: `ready-for-agent`
Type: AFK

## Parent

- `.scratch/pathkey-migration/PRD.md`

## What to build

Migrate note context path types from the private `RelativePath` in `note/paths.rs` to the canonical `PathKey`, and fix anti-pattern string conversions at storage boundaries.

## Corrected Agent Brief

> *This replaces the original agent brief. Generated by AI during triage (2026-06-01).*

**Category:** enhancement
**Summary:** Migrate note context path types from private `RelativePath` to canonical `PathKey`, fixing anti-pattern conversions at storage boundaries.

**Current behavior:**
- `NotePath` in `note/paths.rs` wraps a private `RelativePath(Box<str>)` that parallels but duplicates `PathKey(Box<str>)` from `fs::path`.
- Note storage (read + write) converts `NotePath` → `PathKey` via direct string `PathKey::try_new(path.as_str())` at 6 call sites, bypassing typed filesystem conversions.
- Vault processor converts `PathKey` → `NotePath` via `NotePath::try_new(path.as_str())` at 1 call site.
- Note processor uses `path.as_str()` directly for filesystem I/O.

**Desired behavior:**
- `NotePath` wraps `PathKey` internally, reusing canonical validation and normalization.
- All storage boundary conversions use `NotePath`'s `PathKey` directly instead of re-parsing through `PathKey::try_new`.
- All filesystem I/O boundaries use typed `FilePath`/`DirPath` before conversion.
- The private `RelativePath` type is removed entirely.
- TODO: Consider removing `NotePath` and `FolderPath` entirely once centralized discovery processor is complete — `FileView` will carry path and folder attributes directly.

**Template context (note):** Template repositories and storage use `TemplateId`/`TemplateName` exclusively with NO path-based boundaries. **No changes needed in template context.**

**Key interfaces:**
- `NotePath(RelativePath)` → `NotePath(PathKey)` — internal representation only, public API unchanged.
- `FolderPath(RelativePath)` → `FolderPath(PathKey)` — same pattern.
- Note storage read/write — replace `PathKey::try_new(note.path().as_str())` with access to inner `PathKey`.
- Vault processor — replace `NotePath::try_new(path.as_str())` with typed FS conversion chain.

**Acceptance criteria:**
- [ ] The private `RelativePath` struct in `note/paths.rs` is removed; `NotePath` and `FolderPath` use `PathKey` internally.
- [ ] All note storage boundary conversions (`PathKey::try_new(path.as_str())`) are replaced with direct `PathKey` access.
- [ ] The vault processor `NotePath::try_new(path.as_str())` call uses typed FS conversion via `FilePath`/`DirPath` + `PathKey::from_rooted_path`.
- [ ] Existing archived `NotePath`/`FolderPath` data remains readable (rkyv binary format is compatible — both old and new use `Box<str>`).
- [ ] All existing tests pass without modification (public API unchanged).
- [ ] `PathKey::try_new()` counts in note/storage/ and vault processor are zeroed out.

**Out of scope:**
- Template context (no path-based boundaries exist).
- Broad removal of `RelativePath` outside of note context.
- Schema or vault context migration (already completed in Issues 05/06).
- Changing the public API of `NotePath` or `FolderPath` (internal representation only).
- Creating new `RelativeFilePath`/`RelativeDirPath` types (design discussion deferred).

## TDD & Implementation Plan

### Phase 1: Internal representation change (no public API change)

**1a. `NotePath` wraps `PathKey` internally**

- Replace private `RelativePath(Box<str>)` with `PathKey(Box<str>)` in both `NotePath` and `FolderPath`.
- `NotePath::try_new` chains `.md` extension check + `PathKey::try_new`.
- `FolderPath::try_new` chains hidden-path rejection + `PathKey::try_new`.
- Add `pub(crate) fn as_path_key(&self) -> &PathKey` accessor.
- Remove the private `RelativePath` struct and its `normalize`, `try_new`, `as_str` methods.
- Add a TODO comment: `// TODO: Remove NotePath/FolderPath once centralized discovery processor provides FileView with path/folder attributes.`

**1b. Verify rkyv binary compatibility**

- Both old `RelativePath(Box<str>)` and `PathKey(Box<str>)` serialize as the same bytes. No migration needed.
- Existing tests pass: `cargo nextest run -p lithos-core -- note::paths::tests`

**1c. `FolderPath` wraps `PathKey`**

- Same pattern as `NotePath` — replace `FolderPath(RelativePath)` → `FolderPath(PathKey)`.

### Phase 2: Fix storage anti-patterns

**2a. `note/storage/read.rs`**

- In `find_by_path`: replace `PathKey::try_new(path.as_str())` → `path.as_path_key()` (get inner `&PathKey` directly).
- Add `use super::..` for the new accessor if needed.

**2b. `note/storage/write.rs`**

- `assert_path_available`: same fix.
- `save`, `save_many`: same fix.
- `delete`, `delete_many`: same fix.
- All 5 call sites use direct `PathKey` access instead of re-parsing.

### Phase 3: Fix vault processor

**3a. `vault/processor.rs` `prune()` (line 605)**

- `path` is a `PathKey` from vault repository.
- The vault processor has access to vault root via config.
- Replace `NotePath::try_new(path.as_str())` with typed FS conversion:
  - `FilePath::try_new(absolute_path)?` + `PathKey::from_rooted_path(&root, file_path.as_path())?`
  - Then construct `NotePath` from the resulting path string.
- Actually, since `path` is already a `PathKey` from the vault file view, and we can trust it as valid relative path, the simplest correct fix is to construct `NotePath` directly from the `PathKey`'s string — but the issue correctly identifies that this should use the typed layer. However, the vault context has the root available, so we can construct a `FilePath` from the vault root + path and go through `as_key(root)`.

### Phase 4: Cleanup & verify

- Run `cargo clippy --all-targets --all-features --locked -- -D warnings`.
- Verify zero `PathKey::try_new()` calls in note storage code.

## Additional Scope (from Issue 06 findings)

During vault context migration (Issue 06), we discovered filesystem layer violations where processor code converts paths directly to `PathKey` via string (`PathKey::try_new(raw)`), bypassing the typed filesystem layer (`FilePath`/`DirPath`).

**Correct pattern:**
```rust
// ✅ Good: Typed FS → as_key(root) → PathKey
let file_path = FilePath::try_new(absolute_path)?;
let key = file_path.as_key(root)?;

// ❌ Bad: Direct string conversion
let key = PathKey::try_new(relative_str)?;
```
