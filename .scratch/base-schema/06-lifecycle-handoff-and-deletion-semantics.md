**Key architectural insight:**
- `BaseSchemaProcessor` owns both per-schema resolution (Fresh/New/Stale via `run()`) AND deletion handling (`Deleted` via a new `handle_deletions` static method).
- The existing `SchemaProcessor` batch layer is a temporary wrapper being deleted as part of the processor-split refactor. Do NOT build deletion emission logic into `SchemaProcessor`.
- The caller collects: per-schema resolutions from `BaseSchemaProcessor::run()` + deletion resolutions from `BaseSchemaProcessor::handle_deletions()` → sorts by `SchemaId` → emits combined stream.
- `Deleted` variant on `BaseSchemaResolution` is emitted by a new `BaseSchemaProcessor::handle_deletions()` associated function, which also calls `repository.delete_base_schema()` for each deleted id.
