## What to build

Create the new `BaseSchemaProcessor<P, S>` in `schema/base_processor.rs` matching the `PropertyBankProcessor` typestate orchestration style.

This slice delivers entry flow for missing-view (construct + persist) and present-view (fresh fast-path with timestamp match), without implementing stale-delta behavior.

Return type is `BaseSchemaResolution` (enum with `Fresh` and `New` variants), following the `PropertyBankResolution` naming convention.

## Agent Brief

**Category:** enhancement
**Summary:** Create `BaseSchemaProcessor<P, S>` skeleton with `Init`/`Unknown` entry-state, `from_discovery(...)`, and `run(...)` handling missing-view (construct + persist) and present-view (fresh fast-path) operations.

**Current behavior:**
- `BaseSchema` domain type exists (issue 01).
- `ReadRepository`/`WriteRepository` expose `save_base_schema`, `find_base_schema_by_id`, `find_base_schemas_by_ids`, `delete_base_schema` (issue 02).
- `BASE_SCHEMA_BY_ID` table and `InMemoryRepository`/`RedbRepository` adapters exist (issue 02).
- No processor exists to drive the missing/fresh pipeline; `Builder` cannot yet load base schemas.

**Desired behavior:**
- `BaseSchemaProcessor<P, S>` exists in `lithos-core/src/schema/base_processor.rs` with the dual-typestate pattern matching `PropertyBankProcessor`.
- `PropertyBankProcessor::from_discovery(file: FsFile, root: &DirPath)` derives `PathKey` from file path and root, returning `Result<Self, PathError>`.
- `processor.run(view: Option<&RawSchemaView>, source: &FileReader, repository: &R)` returns `BaseSchemaResolution` — the single-schema handoff envelope:
  - **`None` (missing)**: Constructs a minimal `BaseSchema`, persists via `save_base_schema`, saves `RawSchemaView`, returns `BaseSchemaResolution::New { base_schema }`.
  - **`Some(view)` (present, fast path)**: Timestamp match → `Fresh` with no persistence writes. Returns `BaseSchemaResolution::Fresh { schema_id, base_schema }`.
- Construction of `BaseSchema` from `(SchemaId, SchemaName, PropertyMap, extends, excludes)` — no `RawSchema` parsing in this slice (caller provides finalized inputs).
- `BaseSchemaResolution` enum: `Fresh { schema_id: SchemaId, base_schema: BaseSchema }` (present, unchanged; carries fresh for convenience), `New { base_schema: BaseSchema }` (newly constructed).
- Only fast paths: timestamp match → `Fresh`, no view → `New`. Stale timestamp/content/delta paths deferred to later slice.
- Terminal `NewReady`/`FreshReady` intermediate statuses carry `BaseSchema` for `Completed` stage extraction.
- Stage/status names: `Init`, `Unknown`, `Construction`, `Completed`, `New`, `Fresh`, `NewReady`, `FreshReady` — minimum typestate for this slice. No `Comparison`/`Parsed`/`Analysis` yet.

**Key interfaces (behavioral contract):**
- `BaseSchemaProcessor<P, S>` — generic struct with `file: FsFile`, `path_key: PathKey`, `status: S`, `_stage: PhantomData<P>`. Visibility: `pub(crate)`.
- `BaseSchemaProcessor<Init, Unknown>::from_discovery(file: FsFile, root: &DirPath) -> Result<Self, PathError>`
- `BaseSchemaProcessor<Init, Unknown>::run(self, view: Option<&RawSchemaView>, source: &FileReader, repository: &R) -> Result<BaseSchemaResolution, SchemaLoaderError>`
  - where `R: Repository` (both read + write needed).
- `BaseSchemaResolution` — `pub enum BaseSchemaResolution { Fresh { schema_id: SchemaId, base_schema: BaseSchema }, New { base_schema: BaseSchema } }`, `#[non_exhaustive]`.
- Internal helpers `transition`, `transition_from_parts`, `into_parts` match `PropertyBankProcessor` exactly.
- `Completed::NewReady` → `into_base(self) -> BaseSchema`.
- `Completed::FreshReady` → `into_base(self) -> BaseSchema`.

**Rust implementation constraints:**
- Follow `PropertyBankProcessor` by-reference typestate pattern exactly (struct shape, `transition`/`transition_from_parts`/`into_parts`).
- `pub(crate)` visibility throughout (matches `PropertyBankProcessor`).
- No `unwrap`/`expect` outside tests.
- Repository calls use existing `WriteRepository::save_base_schema` and `WriteRepository::save_raw_schema_view`. View constructed via `RawSchemaView::from_metadata(file.metadata().clone(), path_key)` for the missing path.
- Missing path saves both the `BaseSchema` and the `RawSchemaView`.
- Fresh path reads stored base via `find_base_schema_by_id` (no writes).
- All errors propagate as `SchemaLoaderError`. No new error variants.
- `BaseSchemaResolution` is `#[non_exhaustive]` for future `Stale`/`Deleted` variants.

### Deviations from Plan

1. **Typestate fields use short names**: `NewReady::base` (not `base_schema`), `FreshReady::base` (not `base_schema`), `New::id` (not `schema_id`), `Fresh::id` (not `schema_id`), `FreshReady::id` (not `schema_id`). Field renames applied via refactor commits per user preference.

2. **`SchemaVersion::from_metadata` was REMOVED** (gap in agent brief assumption): The initial implementation fabricated `Blake3Hash::compute(b"")`, hardcoded version/extends/excludes — violating type invariants. Proper view creation requires `RawSchema` from a view extraction pipeline, which doesn't exist yet. View creation is deferred to issue 04.

3. **No stale-timestamp test**: `run_present` has the stale branch (timestamps don't match → reconstruct to `New`), but no test exercises it. Issue 04 adds this.

4. **`_source: &FileReader` unused**: Passed to `run()` per the brief's signature but unused. Designed for content hashing (AC4 "content match") — deferred to issue 04's stale-analysis pipeline.

5. **Test structure flattened**: Tests live under `mod run` directly (not `mod missing`/`mod present` sub-modules). The TDD plan's nested structure was simplified.
