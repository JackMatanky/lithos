# Issue 01: FsFile in PropertyBankProcessor Root

**Parent:** `.scratch/property-bank-processor-deepening/PRD.md` (Candidate 1)

## What to build

Add `file: FsFile` as a root-level field to `PropertyBankProcessor<P, S>`. All status methods derive file identity and metadata from the processor root instead of receiving them as external arguments:

- `self.file.path().as_path()` replaces `config_path: &Path` args
- `self.file.path().as_key(&vault_root)` produces `PathKey` once at construction
- `self.file.metadata()` provides `FileMetadata` for content-freshness comparison

`PropertyBankProcessor::from_fs_file(fs_file)` is the public constructor. `transition()` stays internal for state transitions only.

### Status structs

`PropertyBankProcessor` status structs (`Missing`, `Present`, `Suspect`, `Stale*`, `New`, `Changed`, etc.) keep `FileMetadata` for content-freshness comparison only — they do NOT carry `FilePath`. File identity (`FilePath`) lives at the processor root.

## Acceptance criteria

- [x] `PropertyBankProcessor<P, S>` gains `file: FsFile` private field
- [x] `PathKey` is derived once at construction via `file.path().as_key()` — never `PathKey::try_new()`
- [x] `config_path: &Path` is removed from all method signatures (every `persist`, `parse`, `create`, `update`, `fetch`, `sync_metadata`)
- [x] `path_key: &PathKey` is removed from all method signatures
- [x] All `builder.rs` integration tests pass unchanged (lines 301–394)
- [x] `transition()` retains its internal-only signature — no `file` arg added

## Agent Brief

> *This was generated by AI during triage.*

**Category:** enhancement
**Summary:** Move file identity into `PropertyBankProcessor` root by carrying `FsFile` and removing `config_path`/`path_key` threading from typestate operations.

**Current behavior:**
`PropertyBankProcessor<P, S>` carries only `status` and stage marker. Methods in the typestate flow depend on externally threaded `config_path: &Path` and `path_key: &PathKey`, which duplicates identity context and allows semantic drift between filesystem path and persistence key.

**Desired behavior:**
`PropertyBankProcessor<P, S>` carries `FsFile` as processor root context. Typestate methods derive path and metadata from `self.file`, and derive persistence key from rooted conversion (`as_key(root)`) at the processor boundary instead of constructing ad hoc keys. Status types continue to carry `FileMetadata` for freshness invariants, while file identity remains centralized at processor root.

**Key interfaces:**
- `PropertyBankProcessor<P, S>` — add private `file: FsFile` root field
- `PropertyBankProcessor::from_fs_file(...)` — canonical public constructor for processor identity context
- `PropertyBankProcessor::transition<NP, NS>(...)` — remains internal transition helper and does not accept file identity as an external argument
- Typestate methods (`parse`, `check_timestamps`, `create`, `update`, `fetch`, `sync_metadata`, and any persistence helpers) — stop accepting `config_path` and `path_key` parameters and derive identity from processor context
- `PathKey` derivation — use rooted conversion from `FilePath::as_key(&DirPath)` / `PathKey::from_rooted_path`, never raw `PathKey::try_new` for filesystem-originated keys

**Acceptance criteria:**
- [ ] Processor root contains `FsFile` and typestate transitions preserve this identity context without re-threading path args
- [ ] No typestate method in the property-bank pipeline requires external `config_path` or `path_key`
- [ ] Rooted `PathKey` derivation is used consistently at the processor boundary
- [ ] Existing builder integration behavior remains unchanged (including property-bank load/update/fetch paths)
- [ ] Unit and integration tests covering property-bank orchestration pass under `mise run test:unit` and `mise run test`

**Out of scope:**
- Merging or collapsing stale status variants (`Stale*`) into optional state
- Changing `HashRecord` algorithm or persistence payload format
- Refactoring `SchemaProcessor` flow outside the property-bank processor boundary
