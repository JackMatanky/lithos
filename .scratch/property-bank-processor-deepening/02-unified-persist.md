# Issue 02: Unified persist() HashRecord Source

**Parent:** `.scratch/property-bank-processor-deepening/PRD.md` (Candidate 2)

## What to build

Unify `persist()` so `HashRecord` is always computed from the same `RawPropertyBank` source, regardless of which pipeline path (`New` or `Changed`) created it.

Currently:
- `New::persist` computes from `self.status.raw.properties()` (un-analyzed)
- `Changed::persist` uses `self.status.raw_hash` (analysis-derived)

Move `persist()` to a generic `impl<P, S> PropertyBankProcessor<P, S>` method that takes `(&RawPropertyBank, &PathKey, &WriteRepository)`. Both `New::persist` and `Changed::persist` call the same `persist()` with `&self.status.raw`.

## Acceptance criteria

- [x] `persist()` is generic over any stage — not tied to `New` or `Changed`
- [x] `New::persist` and `Changed::persist` both call same `persist()` with `&self.status.raw`
- [x] Cache view cannot diverge — same `RawPropertyBank` → same `HashRecord`
- [x] Test: `HashRecord` from `New::persist` matches `HashRecord` from `Changed::persist` for same `RawPropertyBank`

## Blocked by

## Implementation notes

- `persist()` signature: `fn persist(&self, raw: &RawPropertyBank, key: &PathKey, repo: &mut impl WriteRepository) -> Result<HashRecord, _>`

- `Changed::persist` passes `self.status.raw` (already present) — not `self.status.raw_hash`
- `HashRecord` computation algorithm does NOT change — only the **source** changes

## Agent Brief

> *This was generated by AI during triage.*

**Category:** enhancement
**Summary:** Consolidate property-bank persistence so `HashRecord` is derived from the same `RawPropertyBank` source in both create (`New`) and update (`Changed`) construction flows.

**Current behavior:**
`PropertyBankProcessor<Construction, New>::persist` computes hashes from `self.status.raw.properties()` and `self.status.content_hash`, while `PropertyBankProcessor<Construction, Changed>::persist` persists `self.status.raw_hash`. The two paths can diverge in source-of-truth semantics even when operating on equivalent raw payloads.

**Desired behavior:**
Introduce one shared persist helper on generic processor impl that accepts `&RawPropertyBank` and computes/persists a `HashRecord` from that single source (plus current content hash contract). Both `New::persist` and `Changed::persist` call this helper with `&self.status.raw`.

**Key interfaces:**
- `PropertyBankProcessor<P, S>` shared helper: `persist(raw, key/repo context, bank)`
- `PropertyBankProcessor<Construction, New>::persist` callsite delegates to shared helper with `&self.status.raw`
- `PropertyBankProcessor<Construction, Changed>::persist` callsite delegates to shared helper with `&self.status.raw`
- `RawPropertyBankView::try_from_raw_with_hashes` remains the persisted view boundary

**Acceptance criteria:**
- [x] Shared persist helper exists on generic processor impl and is reused by both construction branches
- [x] `New::persist` and `Changed::persist` pass `&self.status.raw` to the same helper
- [x] Hash algorithm/output remains unchanged for existing valid inputs; only source unification changes
- [x] Regression test proves equivalent `HashRecord`/persisted raw view hashes between create and update flows for same logical raw payload

**Out of scope:**
- Changing hash algorithms (`Blake3Hash`, property hash computation)
- Altering repository schema/persistence format
- Refactoring discovery/comparison/analysis stage topology
