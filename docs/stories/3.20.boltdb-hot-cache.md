# Story 3.20: Implement BoltDB Hot Cache Adapter

## Status: Draft

## Story

**As a** system architect,
**I want** BoltDB cache adapter storing Note data with IndexTime tracking for sub-millisecond hot path queries and staleness detection,
**so that** we achieve production-grade performance for ByPath, ByBasename, and ByAlias lookups with cache invalidation support in the hybrid storage architecture.

## Acceptance Criteria

1. ✅ Reorganize existing BoltDB cache adapters into `/internal/adapters/spi/cache/boltdb/` subdirectory
2. ✅ BoltDB Writer implements CacheWriterPort for write operations
3. ✅ BoltDB Reader implements both CacheReaderPort and MetadataQueryPort (ByBasename, ByAlias methods)
4. ✅ Define FileDatesDTO in data-models.md for timestamp tracking:
   ```go
   type FileDatesDTO struct {
       ModifiedAt time.Time  // File's modification time (from FileInfo.ModTime)
       IndexedAt  time.Time  // When this note was cached/indexed
   }
   ```
5. ✅ Bucket structure using vault-relative paths as keys:
   - `/notes/` - primary bucket: Path → Note data with FileDatesDTO
   - `/indices/byBasename/` - secondary index: Basename → []Path
   - `/indices/byAlias/` - secondary index: Alias → []Path
   - `/indices/byFileClass/` - secondary index: FileClass → []Path
6. ✅ Staleness detection via IsStale(ctx, path string) (bool, error) method in adapter:
   - Compare filesystem ModTime against cached IndexedAt timestamp
   - Return true if file.ModTime > cached.IndexedAt (file changed since indexing)
   - Handle missing cache entries gracefully (return true - needs indexing)
   - VaultIndexer service calls this method to determine incremental reindexing needs
7. ✅ Atomic writes using `bolt.Tx` transactions
8. ✅ Secondary index maintenance on write (update all indices transactionally)
9. ✅ Performance target: Path/basename/alias lookups < 1ms
10. ✅ Error wrapping per FR9 requirements
11. ✅ Structured logging (zerolog) for all operations
12. ✅ Unit tests: persist/delete/read/list, index queries, error paths, staleness detection
13. ✅ Integration tests: concurrent reads/writes, index consistency, staleness workflow
14. ✅ `golangci-lint run` and `go test` succeed

### Architecture Patterns

**Hybrid Storage Strategy:**
- **BoltDB (Hot Cache):** Stores Note data with IndexTime for staleness detection - fast lookups with cache invalidation
- **SQLite (Deep Storage):** Stores complete frontmatter (full Note data) - for complex queries (Story 3.21)
- **Query Routing:** Hot path queries use BoltDB, complex queries use SQLite (Story 3.22)

**FileDatesDTO Pattern:**
Cache adapters use FileDatesDTO for timestamp tracking and staleness detection:
- **Write:** Extract Note data (Path, Frontmatter, FileClass) + FileDatesDTO(ModifiedAt from VaultFile, IndexedAt = time.Now())
- **Staleness:** Compare filesystem ModTime vs cached.IndexedAt to detect stale entries
- **Separation:** Adapter layer handles staleness detection, service layer calls IsStale() for incremental reindexing

**Secondary Index Pattern:**
BoltDB uses bucket-based secondary indices for O(1) lookups:
- **Primary Bucket:** Path → CachedNote (Path as key, Note data with timestamps)
- **Basename Index:** Basename → []Path (one-to-many, supports duplicates)
- **Alias Index:** Alias → []Path (one-to-many, wikilink resolution)
- **FileClass Index:** FileClass → []Path (one-to-many, schema-based queries)

**Transaction Semantics:**
All index updates happen atomically within a single bolt.Tx transaction:
1. Extract Note data using domain methods (path, frontmatter, fileClass, modifiedAt)
2. Write CachedNote with IndexTime to primary bucket (Path as key)
3. Update basename index (add to array if duplicate)
4. Update alias indices (one entry per alias)
5. Update fileClass index
6. Commit transaction (rollback on any failure)

**Dual Port Implementation Pattern:**
- **CacheWriterPort:** Persist(), Delete() - write-side operations
- **CacheReaderPort + MetadataQueryPort:** Single adapter implementing both interfaces
  - CacheReaderPort: Read(), List() - basic cache operations
  - MetadataQueryPort: ByBasename(), ByAlias(), ByFileClass() - index-based queries

### BoltDB Bucket Schema

```
vault.db (BoltDB)
├── notes/                                (Primary Bucket - Path as key)
│   ├── "notes/contact.md" → NoteWithDates  (Path → Note data with FileDatesDTO)
│   ├── "projects/foo.md" → NoteWithDates
│   └── "ideas/foo.md" → NoteWithDates
│
│   where NoteWithDates = {
│       Path: "notes/contact.md",
│       Frontmatter: {...},
│       FileClass: "contact",
│       FileDates: FileDatesDTO{
│           ModifiedAt: 2025-11-01T10:00:00Z,  // File's modification time from FileInfo
│           IndexedAt: 2025-11-01T10:05:00Z    // When cached/indexed
│       }
│   }
│
└── indices/                              (Secondary Indices)
    ├── byBasename/                       (Basename → []Path, one-to-many)
    │   ├── "contact" → ["notes/contact.md"]
    │   └── "foo" → ["projects/foo.md", "ideas/foo.md"]  (duplicate basenames)
    │
    ├── byAlias/                          (Alias → []Path, one-to-many)
    │   ├── "john-doe" → ["notes/contact.md"]
    │   └── "project-alpha" → ["projects/foo.md"]
    │
    └── byFileClass/                      (FileClass → []Path, one-to-many)
        ├── "contact" → ["notes/contact.md"]
        └── "project" → ["projects/foo.md", "ideas/foo.md"]
```

### Risks and Mitigations

**MEDIUM RISK: BoltDB transaction rollback complexity**
- **Impact:** Complex transaction logic with multiple index updates
- **Mitigation:** Comprehensive error handling; test all rollback scenarios
- **Validation:** Integration tests for transaction failures at each step

**LOW RISK: Index maintenance overhead**
- **Impact:** Multiple index updates per write could slow performance
- **Mitigation:** All updates in single transaction; benchmark to verify < 10ms write time
- **Validation:** Performance benchmarks comparing indexed vs non-indexed writes

**Query Performance:**
- ByPath(): < 1ms (index lookup)
- ByBasename(): < 1ms (index lookup + array scan)
- ByAlias(): < 1ms (index lookup + array scan)
- List(): < 50ms (full bucket scan, 1000 notes)

- Persist(): < 10ms (with all index updates)
- Delete(): < 10ms (with all index cleanups)

- CachedNote: ~500 bytes per note (includes frontmatter, timestamps)
