# Story 3.21: Implement Storage Write Coordination (Unit of Work)

## Status: Draft

## Story

**As a** system architect,
**I want** Unit of Work pattern for coordinated BoltDB + SQLite dual-write operations with transactional guarantees,
**so that** we prevent data inconsistency and ensure atomic writes across hybrid storage systems.

**Unit of Work Pattern**:
1. ✅ Create `/internal/app/cache/unit_of_work.go`:

**Transaction Semantics**:
2. ✅ Batch operations collected during transaction (not immediate writes)

4. ✅ BoltDB write failure → entire transaction rollback (no SQLite write attempted)

6. ✅ Transaction isolation - concurrent transactions don't interfere (mutex)

7. ✅ BoltDB rollback: Use `bolt.Tx.Rollback()`
8. ✅ SQLite rollback: Use SQL `ROLLBACK` statement
9. ✅ Compensating writes: If SQLite fails, delete from BoltDB what was written

**Integration**:
10. ✅ VaultIndexer uses CacheUnitOfWork for all cache writes
11. ✅ CLI commands wrap operations in UoW transactions
12. ✅ Error handling: Proper context, structured logging

**Testing**:
13. ✅ Unit tests: Begin/Commit/Rollback lifecycle
14. ✅ Integration test: Simulate SQLite write failure, verify BoltDB rollback
15. ✅ Integration test: Simulate BoltDB write failure, verify no SQLite write
16. ✅ Concurrency test: Parallel transactions don't interfere
17. ✅ Performance test: Transactional write overhead < 10% vs direct writes

### Architecture Patterns

**Unit of Work Pattern:**
The Unit of Work pattern ensures all-or-nothing writes across two storage systems:
- Batches operations during transaction
- Two-phase commit (BoltDB → SQLite)
- Rollback on any failure (compensating transactions)
- Transaction isolation with mutex

**Transaction Semantics:**
```
Begin() → Batching Phase
  ├─ AddWrite(note1)
  ├─ AddWrite(note2)
  └─ AddDelete(noteID)

Commit() → Two-Phase Commit
  ├─ Phase 1: Write to BoltDB
  │   ├─ Success → Continue to Phase 2
  │   └─ Failure → Rollback entire transaction
  │
  └─ Phase 2: Write to SQLite
      ├─ Success → Transaction complete
      └─ Failure → Compensating rollback (delete from BoltDB)
```

**Compensating Transaction Strategy:**
When SQLite write fails after successful BoltDB write:
1. Collect all successful BoltDB writes
2. Issue compensating DELETE operations to BoltDB
3. Verify compensating deletes succeeded
4. Return error with full context

**Concurrency Safety:**
- Mutex ensures single transaction at a time
- Read operations can proceed concurrently (no lock needed)
- Transaction isolation prevents partial writes

### Operation Batching Design

```go
type operation struct {
    opType operationType  // WRITE or DELETE
    note   domain.Note    // For WRITE operations
    noteID domain.NoteID  // For DELETE operations
}

type operationType int
const (
    opWrite operationType = iota
    opDelete
)

// Batching during transaction
func (uow *CacheUnitOfWork) AddWrite(note domain.Note) error {
    uow.mu.Lock()
    defer uow.mu.Unlock()

    uow.operations = append(uow.operations, operation{
        opType: opWrite,
        note:   note,
    })
    return nil
}

// Commit executes all batched operations
func (uow *CacheUnitOfWork) Commit(ctx context.Context) error {
    uow.mu.Lock()
    defer uow.mu.Unlock()

    }

    // Phase 2: Write to SQLite
    for _, op := range uow.operations {
        // Execute operation on SQLite
    }
}
```

### Risks and Mitigations

**HIGH RISK: Transaction rollback complexity (two storage systems)**
- **Impact:** Complex logic to undo partial writes across systems
- **Mitigation:** Comprehensive error handling; test all failure modes
- **Validation:** Integration tests for each failure scenario

**MEDIUM RISK: Performance impact of transactions**
- **Impact:** Batching and two-phase commit add overhead
- **Mitigation:** Benchmark to ensure < 10% overhead; acceptable for consistency
- **Validation:** Performance tests comparing UoW vs direct writes

**LOW RISK: Compensating transaction failures**
- **Impact:** What if compensating delete from BoltDB fails?
- **Mitigation:** Log critical error; retry logic; manual recovery documentation
- **Validation:** Test compensating transaction failure scenarios
