# Story 3.19: Implement BoltDB Hot Cache Adapter

## Status: Draft

## Story

**As a** system architect,
**I want** BoltDB cache adapter using BoltDBMetadata for sub-millisecond hot path queries,
**so that** we achieve production-grade performance for ByPath, ByBasename, and ByAlias lookups in the hybrid storage architecture.

This story implements the hot cache layer of the hybrid BoltDB+SQLite architecture approved in the November 2, 2024 Sprint Change Proposal. BoltDB provides sub-millisecond lookups for common queries (ByPath, ByBasename, ByAlias) while SQLite handles complex frontmatter queries.

### Architecture Patterns

**Hybrid Storage Strategy:**
- **BoltDB (Hot Cache):** Stores BoltDBMetadata only (Path, Basename, Aliases, FileClass, ModTime) - minimal data for fast lookups
- **SQLite (Deep Storage):** Stores complete frontmatter (full Note data) - for complex queries (Story 3.20)
- **Query Routing:** Hot path queries use BoltDB, complex queries use SQLite (Story 3.22)

**Secondary Index Pattern:**
BoltDB uses bucket-based secondary indices for O(1) lookups:
- **Primary Bucket:** NoteID → BoltDBMetadata (canonical data)
- **Path Index:** Path → NoteID (unique, 1:1 mapping)
- **Basename Index:** Basename → []NoteID (one-to-many, supports duplicates)
- **Alias Index:** Alias → []NoteID (one-to-many, wikilink resolution)
- **FileClass Index:** FileClass → []NoteID (one-to-many, schema-based queries)

**Transaction Semantics:**
All index updates happen atomically within a single bolt.Tx transaction:
1. Write BoltDBMetadata to primary bucket
2. Update path index
3. Update basename index (add to array if duplicate)
4. Update alias indices (one entry per alias)
5. Update fileClass index
6. Commit transaction (rollback on any failure)

**CQRS Port Implementation:**
- **CacheWriterPort:** Persist(), Delete() - write-side operations
- **CacheReaderPort:** ByPath(), ByBasename(), ByAlias(), List() - read-side queries

### BoltDB Bucket Schema

```
vault.db (BoltDB)
├── notes/                          (Primary Bucket)
│   ├── note-001 → BoltDBMetadata   (NoteID → BoltDBMetadata)
│   ├── note-002 → BoltDBMetadata
│   └── note-003 → BoltDBMetadata
│
└── indices/                        (Secondary Indices)
    ├── byPath/                     (Path → NoteID, unique)
    │   ├── "notes/contact.md" → "note-001"
    │   ├── "projects/foo.md" → "note-002"
    │   └── "ideas/foo.md" → "note-003"
    │
    ├── byBasename/                 (Basename → []NoteID, one-to-many)
    │   ├── "contact" → ["note-001"]
    │   └── "foo" → ["note-002", "note-003"]  (duplicate basenames)
    │
    ├── byAlias/                    (Alias → []NoteID, one-to-many)
    │   ├── "john-doe" → ["note-001"]
    │   └── "project-alpha" → ["note-002"]
    │
    └── byFileClass/                (FileClass → []NoteID, one-to-many)
        ├── "contact" → ["note-001"]
        └── "project" → ["note-002", "note-003"]
```

### Risks and Mitigations

**MEDIUM RISK: BoltDB transaction rollback complexity**
- **Impact:** Complex transaction logic with multiple index updates
- **Mitigation:** Comprehensive error handling; test all rollback scenarios
- **Validation:** Integration tests for transaction failures at each step

**LOW RISK: Index maintenance overhead**
- **Impact:** Multiple index updates per write could slow performance
- **Mitigation:** All updates in single transaction; benchmark to verify < 10ms write time
- **Validation:** Performance benchmarks comparing indexed vs non-indexed writes

### Performance Targets

**Query Performance:**
- ByPath(): < 1ms (index lookup)
- ByBasename(): < 1ms (index lookup + array scan)
- ByAlias(): < 1ms (index lookup + array scan)
- List(): < 50ms (full bucket scan, 1000 notes)

**Write Performance:**
- Persist(): < 10ms (with all index updates)
- Delete(): < 10ms (with all index cleanups)

**Memory Usage:**
- BoltDBMetadata: ~200 bytes per note (minimal)
- Total cache size: ~200KB for 1000 notes
