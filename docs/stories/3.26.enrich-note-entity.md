### Architecture Patterns

**Entity Enrichment Pattern (per data-model spec):**
- `Note.Path` is the identity (vault-relative string). `NoteID` no longer exists.
- Parsed metadata (`Frontmatter`, `Links`, `Headings`, `Tags`, `Tasks`) lives on the entity directly; `Backlinks` are populated later.
- Rich methods expose validated behavior instead of leaking `Frontmatter.Fields`.

**Two-Phase Population Workflow:**
1. **Phase 1 (Parsing):** MarkdownParserAdapter parses markdown once and calls `NewNote(path, fm, links, headings, tags, tasks)` which returns a validated note with `Backlinks` empty.
2. **Phase 2 (Enrichment):** BacklinkService (and future enrichers) compute derived information and update `Backlinks` only, keeping other metadata immutable.

**Law of Demeter Compliance:**
Delegation methods prevent services from digging through nested structures:
```go
// BAD
note.Frontmatter.Fields["title"].(string)

// GOOD
note.GetFrontmatterString("title")
```

**Domain-Driven Design Alignment:**
- Encapsulated aggregate with identity (Path) and value objects (Frontmatter, Link, Heading, TaskItem).
- Factory + validation ensures consistency with architecture data-model expectations.

### Implementation Notes

**Phase 0: Structural Alignment**
Mirror the data-model blueprint by embedding `Frontmatter`, `Links`, `Headings`, `Tags`, `Tasks`, and `Backlinks` on the entity and by using `Path string` as the identifier. Remove `NoteID` throughout the codebase.

**Phase 1: Validation Method**
Implement `Note.Validate()` for semantic validation: ensure `Path` is vault-relative + non-empty, `Frontmatter` is non-nil, parsed slices are initialized (not nil), and `Backlinks` mutations only occur during the enrichment phase.

**Phase 2: Factory Constructor**
Create `NewNote(path string, frontmatter Frontmatter, links []Link, headings []Heading, tags []string, tasks []TaskItem)` that enforces validation at creation and guarantees `Backlinks` starts empty. Provide a deliberate helper for enrichment (e.g., `note.WithBacklinks(backlinks []Link) Note`) to keep the two-phase workflow explicit.

**Phase 3: Delegation Methods**
Add convenience methods delegating to Frontmatter: `HasFrontmatterField()`, `GetFrontmatterString()`, plus strongly-typed wrappers for `FileClass()`, `Title()`, and `Aliases()` described in the architecture doc. Each helper returns `(value, bool)` or `(value, error)` and uses a shared `NoteFieldError` so callers can distinguish missing data from unexpected type mismatches without panics.

**Phase 4: Service Integration**
Update MarkdownParserAdapter, BacklinkService, QueryService, and any other consumers so they use the factory, validation, and delegation helpers instead of touching internal struct fields directly.

### Risks and Mitigations

**LOW RISK: Delegation method explosion**
- **Impact:** Too many convenience methods clutter API
- **Mitigation:** Only add frequently-used delegations; document when to access Frontmatter directly
- **Validation:** Code review for API clarity

**LOW RISK: Validation complexity**
- **Impact:** Note.Validate() may become complex with many business rules
- **Mitigation:** Extract validation strategies if complexity grows
- **Validation:** Monitor cyclomatic complexity; refactor if > 10

**LOW RISK: Two-phase contract drift**
- **Impact:** Adapters might start mutating parsed slices after enrichment, violating the architecture doc.
- **Mitigation:** Keep `NewNote` returns immutable slices (copy when needed) and limit mutators to `Backlinks`.
- **Validation:** Integration tests should assert that parsed metadata never changes between parsing + enrichment phases.
