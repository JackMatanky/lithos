# Story 3.18: MarkdownParserPort - Dedicated Parsing Port & Adapter

## Status: Draft

## Story

**As a** system architect,
**I want** a dedicated MarkdownParserPort and MarkdownParserAdapter to move goldmark parsing from domain to adapter layer,
**so that** we fix hexagonal architecture violations and maintain clean separation between syntactic (adapter) and semantic (domain) validation.

## Acceptance Criteria

**New Port Definition**:
1. ✅ Create `/internal/ports/spi/markdown.go`:
   ```go
   type MarkdownParserPort interface {
       // ParseFrontmatter extracts YAML frontmatter from markdown content
       // Returns parsed fields as map, error if invalid YAML
       ParseFrontmatter(ctx context.Context, content []byte) (map[string]any, error)
   }
   ```

**New Adapter Implementation**:
2. ✅ Create `/internal/adapters/spi/vault/markdown.go`:
   ```go
   type MarkdownParserAdapter struct {
       markdown goldmark.Markdown
       log      zerolog.Logger
   }

   func (a *MarkdownParserAdapter) ParseFrontmatter(ctx context.Context, content []byte) (map[string]any, error) {
       // Use goldmark + frontmatter extension
       // Syntactic validation (YAML structure)
       // Return parsed map or error
   }
   ```

**Domain Layer Cleanup**:
3. ✅ Remove goldmark imports from `internal/app/frontmatter/service.go`
4. ✅ Remove `FrontmatterService.Extract()` method entirely
5. ✅ FrontmatterService constructor accepts `MarkdownParserPort` (injected dependency)
6. ✅ FrontmatterService focuses on **semantic validation only** (schema compliance)

**Adapter Layer - Syntactic Validation**:
7. ✅ MarkdownParserAdapter performs **syntactic validation**:
   - YAML structure validation
   - Parsing errors (malformed YAML)
   - Returns structured errors with line numbers

**Integration**:
8. ✅ Update VaultIndexer to inject MarkdownParserPort
9. ✅ VaultIndexer workflow: Read file → Parse frontmatter → Pass to FrontmatterService
10. ✅ VaultReaderAdapter.Read() still returns raw Content (parsing happens in indexer)

**Testing**:

12. ✅ Unit tests: MarkdownParserAdapter syntactic validation
13. ✅ Integration tests: End-to-end parsing workflow
14. ✅ Error handling tests: Malformed YAML, missing frontmatter

### Architecture Patterns

**File Location (YAGNI Principle):**
MarkdownParserAdapter is implemented in `internal/adapters/spi/vault/markdown.go` (NOT in a separate markdown/ package) because:
- Markdown parsing is ONLY used by vault operations in Epic 3
- YAGNI (You Aren't Gonna Need It): Don't create separate package until actually needed elsewhere
- Keeps codebase simpler and more maintainable
- If future features need markdown parsing, we can extract to separate package then

**Hexagonal Architecture Compliance:**
This story fixes a critical hexagonal architecture violation where goldmark (infrastructure) was used directly in the domain layer (FrontmatterService). The new design properly separates:
- **Adapter Layer (Syntactic):** MarkdownParserAdapter - YAML parsing, structure validation
- **Domain Layer (Semantic):** FrontmatterService - Schema compliance, business rules

**Validation Layer Separation (from coding-standards.md):**

| Layer | Concern | Responsibility | Method Names |
|-------|---------|----------------|--------------|
| **Adapter (Syntactic)** | Structure, format | YAML parsing, delimiter detection | `ValidateSyntax()`, `IsValidStructure()` |
| **Domain (Semantic)** | Business rules | Schema compliance, required fields | `Validate()`, `IsSchemaCompliant()` |

**Port/Adapter Pattern:**
- MarkdownParserPort (SPI): Contract defined by domain needs
- MarkdownParserAdapter: Implementation using goldmark library
- Future adapters possible (e.g., CommonMarkAdapter) without domain changes

**Dependency Injection:**
FrontmatterService receives MarkdownParserPort via constructor injection, enabling:
- Pure domain testing with mock parser
- Adapter swapping without domain changes
- Clear separation of concerns
