# Story 6.1: VaultIndexer Decomposition - Event-Driven Architecture

## Status

ready-for-dev

## Story

**As a** developer,
**I want** VaultIndexer decomposed into focused, event-driven components,
**so that** the 938-line god-object becomes maintainable, testable, and extensible.

## Context

**Current Problem:**
VaultIndexer is a 938-line god-object with 22 methods handling:
- File discovery & scanning
- Markdown parsing orchestration
- Validation orchestration
- Cache writing (BoltDB + SQLite)
- Event publishing
- Error handling & stats tracking
- Unit of work pattern
- Progress reporting

This violates Single Responsibility Principle and makes testing, debugging, and extending the system difficult.

**Refactoring Goal:**
Decompose into event-driven components where each component:
1. Has a single, well-defined responsibility
2. Communicates via domain events
3. Can be tested in isolation
4. Can be replaced/extended without affecting others

**Target Architecture:**
```
VaultIndexer (Core Coordinator - 100 lines)
├── FileScannerService (150 lines) - File discovery
├── NoteProcessingPipeline (200 lines) - Parse→Validate→Cache orchestration
│   ├── MarkdownParsingStage
│   ├── ValidationStage
│   └── CachingStage
├── IndexingEventPublisher (50 lines) - Event publishing
└── IndexStatsCollector (50 lines) - Metrics & observability
```

## Dev Notes

### Architecture Alignment

From `docs/architecture/components.md`:

VaultIndexer should follow event-driven architecture patterns established in Epic 3. Components communicate via domain events for loose coupling and testability.

### Event Types

**New Events:**
- **FileDiscoveredEvent:** Published by FileScannerService when file is found
- **NoteIndexedEvent:** Published by NoteProcessingPipeline on successful indexing
- **NoteIndexingFailedEvent:** Published by NoteProcessingPipeline on errors

**Existing Events (reused):**
- **VaultIndexingStartedEvent:** Published by IndexingEventPublisher
- **VaultIndexingCompleteEvent:** Published by IndexingEventPublisher
- **VaultIndexingFailedEvent:** Published by IndexingEventPublisher

### Component Responsibilities

**FileScannerService:**
- File system traversal
- Excluded directory filtering
- File discovery event publishing

**NoteProcessingPipeline:**
- Async file processing with worker pool
- Parsing stage delegation
- Validation stage delegation
- Caching stage delegation
- Error handling & recovery

**IndexingEventPublisher:**
- Event creation with metrics
- Event publishing to EventBus
- No business logic

**IndexStatsCollector:**
- Thread-safe stat aggregation
- Real-time metrics
- Final summary generation

**VaultIndexer (Core):**
- Component lifecycle management
- High-level workflow orchestration
- No business logic

### Testing Strategy

- **Unit Tests:** Each component tested in isolation with mocks
- **Integration Tests:** End-to-end event flow verification
- **Performance Tests:** Bounded concurrency validation
- **Regression Tests:** All existing tests must pass

### Common Pitfalls

- Don't put business logic in VaultIndexer coordinator
- Ensure event publishing is async and non-blocking
- Use bounded concurrency to prevent resource exhaustion
- Handle errors gracefully in each pipeline stage
- Maintain thread safety in IndexStatsCollector

### Migration Path

1. Create new components alongside existing VaultIndexer
2. Write tests for new components first
3. Gradually migrate logic from old to new
4. Update DI container to wire new components
5. Delete old implementation when all tests pass
