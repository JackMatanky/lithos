# Story 4.5: Template Function FileClass

## Status

Ready for Implementation

## Story

**As a** developer,
**I want** TemplateEngine to expose a fileClass template function,
**so that** templates can access a note's schema classification for conditional logic.

## Acceptance Criteria

**Template Function Implementation:**

- 4.5.1: TemplateEngine exposes `fileClass` function: `{{fileClass noteID}}` returns schema name for given note
- 4.5.2: Function accepts NoteID parameter (string basename or full path)
- 4.5.3: Function delegates to QueryService to retrieve note's fileClass from frontmatter
- 4.5.4: Function returns schema name (e.g., "contact", "project") or empty string if note not found

**Schema Integration:**

- 4.5.5: Function works with schema-driven notes that have fileClass property
- 4.5.6: Function supports both explicit fileClass values and schema-inferred classifications
- 4.5.7: Function handles notes without fileClass field gracefully (returns empty string)

**Error Handling:**

- 4.5.8: Function handles invalid NoteID parameters (non-existent notes) without crashing
- 4.5.9: Function logs debug information for troubleshooting per coding standards
- 4.5.10: Function includes GoDoc documentation referencing FR9 schema-driven requirements

**Testing:**

- 4.5.11: Unit tests cover function registration, successful lookups, missing notes, and error cases
- 4.5.12: Integration tests verify end-to-end functionality with real QueryService and vault data
- 4.5.13: All tests pass: `go test ./internal/app/template`

**Quality Gates:**

- 4.5.14: Linting passes: `golangci-lint run --fix internal/app/template`
- 4.5.15: Code coverage >90% for fileClass function
- 4.5.16: Committed with message: `feat(template): add fileClass function for schema-driven conditional logic`

## Dev Notes

### Architecture Alignment (v0.6.8)

From `docs/architecture/components.md#templateengine`:

Template functions should enable schema-driven conditional logic. The fileClass function allows templates to check note classifications for conditional rendering based on schema types.

### Testing Strategy

From `docs/architecture/testing-strategy.md`:

- Unit tests for template function logic with mock QueryService
- Integration tests for end-to-end functionality with real vault data
- Error handling tests for invalid NoteID parameters
- Coverage requirements: >90% for function implementation

### TDD Workflow

- RED: Write failing tests first (fileClass lookups, error cases)
- GREEN: Implement minimal code to pass tests
- REFACTOR: Improve code quality while maintaining test passes

### Common Pitfalls

- Don't crash on invalid NoteID - handle gracefully
- Don't expose internal QueryService errors - wrap appropriately
- Don't assume fileClass exists - handle missing field
- Don't block template rendering on lookup failures - fail fast with empty string
