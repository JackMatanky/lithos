## Story

**As a** system architect,
**I want** Unit of Work pattern for coordinated BoltDB + SQLite dual-write operations with transactional guarantees,
**so that** we prevent data inconsistency and ensure atomic writes across hybrid storage systems.

## Acceptance Criteria

**Unit of Work Pattern**:
1. ✅ Create `/internal/app/vault/unit_of_work.go`:
   ```go
   type CacheUnitOfWork struct {
       boltWriter   spi.CacheWriterPort
       sqliteWriter spi.CacheWriterPort
       operations   []operation
       mu           sync.Mutex
   }

   func (uow *CacheUnitOfWork) Begin() error
   func (uow *CacheUnitOfWork) AddWrite(note domain.Note, indexTime time.Time) error
   func (uow *CacheUnitOfWork) AddDelete(path string) error
   func (uow *CacheUnitOfWork) Commit(ctx context.Context) error
   func (uow *CacheUnitOfWork) Rollback(ctx context.Context) error
   ```

**Transaction Semantics**:
2. ✅ Batch operations collected during transaction (not immediate writes)
3. ✅ IndexTime consistency: Single indexTime parameter passed to AddWrite() is propagated to both BoltDB and SQLite writers (ensures identical timestamps across storages)
4. ✅ Commit sequence: BoltDB first, then SQLite (hot cache priority)
5. ✅ BoltDB write failure → entire transaction rollback (no SQLite write attempted)
6. ✅ SQLite write failure → rollback BoltDB changes (compensating transaction)
7. ✅ Transaction isolation - concurrent transactions don't interfere (mutex)

**Rollback Strategy**:
8. ✅ BoltDB rollback: Use `bolt.Tx.Rollback()`
9. ✅ SQLite rollback: Use SQL `ROLLBACK` statement
10. ✅ Compensating writes: If SQLite fails, delete from BoltDB what was written

**Integration**:
11. ✅ VaultIndexer uses CacheUnitOfWork for all cache writes
12. ✅ CLI commands wrap operations in UoW transactions
13. ✅ Error handling: Proper context, structured logging

**Testing**:

### Architecture Patterns

**Unit of Work Pattern:**
The Unit of Work pattern ensures all-or-nothing writes across two storage systems:
- Batches operations during transaction
- Two-phase commit (BoltDB → SQLite)
- Rollback on any failure (compensating transactions)
- Transaction isolation with mutex

**Transaction Semantics:**
```
Begin() → Batching Phase
  ├─ AddWrite(note1, indexTime)
  ├─ AddWrite(note2, indexTime)
  └─ AddDelete(path)

Commit() → Two-Phase Commit
  ├─ Phase 1: Write to BoltDB
  │   ├─ Success → Continue to Phase 2
  │   └─ Failure → Rollback entire transaction
  │
  └─ Phase 2: Write to SQLite
      ├─ Success → Transaction complete
      └─ Failure → Compensating rollback (delete from BoltDB)
```

**Compensating Transaction Strategy:**
When SQLite write fails after successful BoltDB write:
1. Collect all successful BoltDB writes
2. Issue compensating DELETE operations to BoltDB
3. Verify compensating deletes succeeded
4. Return error with full context

**Concurrency Safety:**
- Mutex ensures single transaction at a time
- Read operations can proceed concurrently (no lock needed)
- Transaction isolation prevents partial writes

### Operation Batching Design

**Interface-Based Operation Design:**
```go
// Operation interface for extensible operation types
type Operation interface {
    Execute(ctx context.Context, writer spi.CacheWriterPort) error
    Rollback(ctx context.Context, writer spi.CacheWriterPort) error
    Type() OperationType
}

// Concrete operation implementations
type WriteOperation struct {
    note      domain.Note
    indexTime time.Time
}

type DeleteOperation struct {
    noteID domain.NoteID
}

// Strategy pattern for transaction execution
type TransactionStrategy interface {
    Execute(ctx context.Context, operations []Operation, writers []spi.CacheWriterPort) error
}

// Batching during transaction
func (uow *CacheUnitOfWork) AddWrite(note domain.Note, indexTime time.Time) error {
    uow.mu.Lock()
    defer uow.mu.Unlock()

    uow.operations = append(uow.operations, NewWriteOperation(note, indexTime))
    return nil
}

// Commit delegates to strategy pattern
func (uow *CacheUnitOfWork) Commit(ctx context.Context) error {
    uow.mu.Lock()
    defer uow.mu.Unlock()

    // Execute using configured transaction strategy
    return uow.strategy.Execute(ctx, uow.operations, nil)
}
```

**Key Architectural Improvements:**
- **Extensibility**: New operation types don't require modifying existing code
- **Testability**: Each operation can be tested in isolation
- **Flexibility**: Transaction strategies can be swapped for different consistency models
- **Maintainability**: Clear separation between operation logic and transaction coordination

**Execution Sequence (textual outline):**
1. Collect operations via `AddWrite`/`AddDelete`, preserving call order for deterministic commits.
2. When `Commit` executes, start the BoltDB transaction and apply each cached operation with the stored `indexTime`.
3. After BoltDB succeeds, replay the same operation slice against SQLite so both stores share timestamps and order.
4. If BoltDB fails, abort immediately—SQLite writers never run and the buffered operations remain for inspection.
5. After SQLite succeeds, clear buffered operations so repeat commits do not replay stale writes.
6. If SQLite fails after BoltDB succeeds, invoke the compensating rollback routine from Phase 3 to keep caches in sync (delete/rewind operations as needed).

### 2. Read-Before-Op Rollback Enhancement (2 points)

**Status:** ❌ OPTIONAL IMPROVEMENT (future recommendation)

The gate suggests implementing "Read-Before-Op for precise rollback restoration" in `internal/app/vault/unit_of_work.go`.

**Current Limitation:**
DeleteOperation rollback is a no-op because we don't read the original note before deletion:

```go
func (op *DeleteOperation) Rollback(
    ctx context.Context,
    writer spi.CacheWriterPort,
) error {
    // Cannot undo delete easily without read-before-delete
    return nil
}
```

**Proposed Enhancement:**

1. **Modify DeleteOperation to capture original state:**
   ```go
   type DeleteOperation struct {
       noteID       domain.NoteID
       originalNote *domain.Note  // Captured before deletion
       indexTime    time.Time     // Captured before deletion
   }
   ```

2. **Update AddDelete to read-before-delete:**
   ```go
   func (uow *CacheUnitOfWork) AddDelete(ctx context.Context, path string, reader spi.CacheReaderPort) error {
       uow.mu.Lock()
       defer uow.mu.Unlock()

       // Read original note before deletion
       noteID := domain.NoteID(path)
       originalNote, err := reader.Read(ctx, noteID)
       if err != nil {
           // Note doesn't exist - still queue delete (idempotent)
           uow.operations = append(uow.operations, NewDeleteOperation(noteID, nil, time.Time{}))
           return nil
       }

       // Extract indexTime from original note metadata
       indexTime := extractIndexTime(originalNote)
       uow.operations = append(uow.operations, NewDeleteOperation(noteID, &originalNote, indexTime))
       return nil
   }
   ```

3. **Implement proper DeleteOperation rollback:**
   ```go
   func (op *DeleteOperation) Rollback(
       ctx context.Context,
       writer spi.CacheWriterPort,
   ) error {
       if op.originalNote == nil {
           // Nothing to restore
           return nil
       }
       // Restore original note with original indexTime
       return writer.Persist(ctx, *op.originalNote, op.indexTime)
   }
   ```

**Trade-offs:**
- ✅ **Pro:** Precise rollback restoration, better data integrity
- ✅ **Pro:** Idempotent delete operations
- ❌ **Con:** Additional read I/O on every delete (performance impact)
- ❌ **Con:** Increased memory footprint (storing original notes)
- ❌ **Con:** API change - AddDelete signature changes to require reader

**Recommendation:**
This is a **future enhancement** not critical for cache semantics. The current delete-based rollback is acceptable because:
- Cache is eventually consistent (reindexing will repair)
- Delete operations are rare in typical workflows
- Performance impact outweighs benefit for cache layer

3. Implement proper Rollback using originalNote
4. Update tests to cover restore-on-rollback scenarios

6. Document trade-offs in code comments

**Estimated Effort:** 4-6 hours (implementation + tests + benchmarks)
