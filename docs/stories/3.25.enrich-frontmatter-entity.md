# Story 3.25: Enrich Frontmatter Entity with Validation & Factory

## Status: Approved

## Story

**As a** system architect,
**I want** Frontmatter transformed from anemic data bag into rich domain entity with validation and factory methods,
**so that** we enable proper domain modeling with type-safe field access and enforced validation.

## Acceptance Criteria

1. ✅ `NewFrontmatter(fields map[string]any) Frontmatter` returns a defensively-copied value object that preserves every parsed field exactly as delivered by the adapter (no validation side effects).
2. ✅ Frontmatter exposes generic helpers documented in `docs/architecture/data-models.md#frontmatter`: `Get(key) (any, bool)` and `Has(key string) bool` without panicking on missing keys.
3. ✅ Type inspector helpers exist (`IsString`, `IsArray`, `IsInt`, `IsBool`, `IsMap`) so callers can branch safely before casting.
4. ✅ Domain-level delegation helpers (`FileClass()`, `Title()`, `Aliases()`) encapsulate common access patterns and use the Config singleton for `FileClassKey` lookups.
5. ✅ Frontmatter instances are immutable after construction (helpers never mutate `Fields`), and all constructors in the codebase call `NewFrontmatter`.
6. ✅ FrontmatterService (and other consumers such as TemplateEngine and QueryService) use these helpers instead of reaching into `Fields` directly.
7. ✅ Unit + integration tests cover the helper methods, Config dependency, and consumer updates.

### Architecture Patterns

**Entity Enrichment Pattern (per architecture data models):**
- Frontmatter is an immutable value object that wraps the parsed YAML map and exposes helper methods.
- Enrichment focuses on type-safe access (`Get`, `Has`, `IsString/Array/Int/Bool/Map`) and domain-friendly delegation helpers (`FileClass`, `Title`, `Aliases`).
- Validation remains the responsibility of `FrontmatterService`; the entity simply provides safe access to already-parsed data.

**Domain-Driven Design:**
- **Value Object:** Two Frontmatter instances with identical `Fields` are equivalent.
- **Immutability:** `NewFrontmatter` defensively copies the map so helpers cannot mutate adapter output.
- **Config Awareness:** Delegation helpers may read the Config singleton (allowed per doc) but never persist configuration in the entity itself.

**Validation Strategy Alignment:**
- **Syntactic:** MarkdownParserAdapter + FrontmatterDTO handle YAML parsing/structure.
- **Semantic:** `FrontmatterService.IsSchemaCompliant` enforces schema rules using the helper methods provided here.

### Implementation Notes

**Phase 1: Factory Constructor**
Implement `NewFrontmatter(fields map[string]any) Frontmatter` that copies the provided map (handles `nil`, cleans up whitespace if needed) and guarantees immutability.

**Phase 2: Generic Helpers**
Add `Get`, `Has`, and the type inspectors. Keep them panic-free and table-driven so services can pattern-match YAML values confidently.

**Phase 3: Delegation Helpers**
Add the documented helpers (`FileClass()`, `Title()`, `Aliases()`) leveraging Config.FileClassKey and normalizing slices into `[]string`.

**Phase 4: Integration**
Update FrontmatterService and other consumers to call these helpers instead of poking at `Fields` directly. This reduces duplication and enforces Law of Demeter.

### Risks and Mitigations

**LOW RISK: Type assertion panics in accessors**
- **Impact:** Runtime panics if helpers cast without checking
- **Mitigation:** All helpers return `(value, bool)`; tests must include mixed-type YAML cases
- **Validation:** Table-driven tests for every helper / type combination

**LOW RISK: Config dependency misuse**
- **Impact:** Helpers might read Config before it is initialized
- **Mitigation:** Document helper usage and ensure Config singleton is initialized before the parser constructs Frontmatter
- **Validation:** Integration tests that call `FileClass()`/`Aliases()` under both default and custom `FileClassKey`
