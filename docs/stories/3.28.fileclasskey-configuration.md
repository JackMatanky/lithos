### Architecture Patterns

**Configuration Pattern:**
FileClassKey enables schema flexibility without code changes:
- **Default:** "fileClass" (standard Obsidian convention)
- **Custom:** "type", "category", "kind" (vault-specific conventions)
- **Flexibility:** Support diverse vault schemas

**Single Responsibility:**
Config struct centralizes configuration management:
```go
type Config struct {
    VaultPath    string
    FileClassKey string // Default: "fileClass"
    CachePath    string
}
```

**Fail-Fast Validation:**
Config validation catches issues at startup:
- Non-empty FileClassKey required
- Clear error messages for misconfiguration

### Implementation Notes

**Phase 1: Config Field Addition**
Add FileClassKey field to Config struct with default "fileClass".

**Phase 2: Validation**
Add validation ensuring FileClassKey is non-empty.

**Phase 3: Usage Migration**
Find all hardcoded "fileClass" references and replace with Config.FileClassKey.

**Phase 4: Documentation**
Document fileClass key customization in architecture docs.

### Risks and Mitigations

**MEDIUM RISK: Hardcoded "fileClass" references remain**
- **Impact:** Custom fileClass keys won't work if hardcoded references missed
- **Mitigation:** Comprehensive grep for "fileClass" string literals; replace all with config
- **Validation:** Integration test with custom fileClass key (e.g., "type")

**LOW RISK: Default value not applied**
- **Impact:** Empty FileClassKey if not set in config
- **Mitigation:** Validation ensures non-empty; default value in constructor
- **Validation:** Unit tests for default value application
