# Validation (`access` vs `access_unchecked`)

Validation is critical when memory-mapping byte buffers directly to structs. Treating random bytes as an `Archived<T>` without verification can lead to undefined behavior, panics, and severe memory safety vulnerabilities.

**Ref:** [rkyv Validation Guide](https://rkyv.org/validation.html)
**Ref:** [`bytecheck` module docs](https://docs.rs/rkyv/latest/rkyv/validation/index.html)

## `access` (Safe API)
The [`rkyv::access`](https://docs.rs/rkyv/latest/rkyv/fn.access.html) API mathematically validates the buffer against the invariants of the `Archived<T>` struct before returning a reference.
- **What it checks**: Pointer alignment, boundary limits, UTF-8 validity for strings, and valid enum discriminants.
- **When to use**: *Always* use this at system boundaries. This includes data arriving over network protocols, untrusted user inputs, and file formats loaded directly from disk.
- **Requirement**: This runtime validation requires the `bytecheck` feature flag in `Cargo.toml`.

```rust
use rkyv::access;

// The buffer undergoes strict validation before reference is granted
let archived = access::<ArchivedData, rkyv::rancor::Error>(&bytes)?;
```

## `access_unchecked` (Unsafe API)
The [`rkyv::access_unchecked`](https://docs.rs/rkyv/latest/rkyv/fn.access_unchecked.html) API completely bypasses all validation overhead, yielding instantaneous memory access.
- **When to use**: ONLY for strictly trusted internal data or pre-validated paths. It is invaluable for high-performance internal caches (e.g., Redb queries) where the source of the bytes is guaranteed to have been generated by your system's serialization routines.
- **Warning**: Using this on untrusted or corrupted data invokes undefined behavior immediately.

```rust
use rkyv::access_unchecked;

// UNSAFE: Only use if you absolutely trust the bytes layout
let archived = unsafe { access_unchecked::<ArchivedData>(&bytes) };
```

## Applicability: When is Validation Too Expensive?
Validation is zero-allocation, but recursive bounds-checking introduces CPU overhead.
- **Too Expensive**: In extremely tight CPU hot-paths where validating deeply nested structures introduces unacceptable latency, especially for internal, trusted data.
- **The Tradeoff**: If passing buffers locally between trusted processes or reading from a secure embedded DB layer, skip validation via `access_unchecked`. If accepting network payloads from untrusted users, validation is strictly necessary to prevent memory unsafety or out-of-bounds pointer reads.

## Lithos Guideline: Trust Boundaries
In the Lithos architecture, validation is applied based on the trust level of the source:
- **Untrusted Boundaries (Use `access`)**: File ingestion layers (`FsReader`, `ingestor.rs`), CLI inputs, or if we ever load `rkyv` snapshots from the user's filesystem.
- **Trusted Boundaries (Use `access_unchecked`)**: Reads from our internal `redb` databases. Since `lithos-core` exclusively writes to `redb`, we implicitly trust the structural integrity of those byte arrays. This allows us to achieve maximum performance on CQRS reads.

## Validation Scaling
The computational cost of `access` scales linearly with the complexity of your struct.
- **Best Practice**: Validate exclusively at the system boundary (e.g., upon reading from disk or network). Once validated, cache the reference or buffer and use `access_unchecked` (if strictly controlled) for downstream access. Do not repeatedly validate the same buffer.
