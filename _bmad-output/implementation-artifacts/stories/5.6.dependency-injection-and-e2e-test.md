# Story 5.6: Dependency Injection and E2E Test for Interactive Input Engine

## Status

Draft

## Story

**As a** developer,
**I want** to implement dependency injection for the interactive input engine components and add comprehensive e2e tests,
**so that** the interactive input functionality is properly wired and thoroughly tested end-to-end.

## Context

This story completes the interactive input engine (Epic 5) by wiring all components through dependency injection and ensuring the entire interactive workflow works correctly through e2e testing. It follows the same TDD pattern established in stories 5.1-5.5 and the DI/e2e pattern from story 1.16 for the foundational CLI.

## Acceptance Criteria

**Functional Requirements:**

- 5.6.1: All interactive input components (prompt port, promptui adapter, finder port, fuzzyfind adapter, CLI find command, template engine helpers) are properly registered in the DI container
- 5.6.2: The main.go file includes interactive input engine dependencies in the application wiring
- 5.6.3: E2E tests cover the complete interactive input workflow from CLI command execution through user prompts to template engine integration
- 5.6.4: The e2e tests use real terminal interactions and validate actual interactive behavior
- 5.6.5: Test scenarios include various user input patterns and edge cases

**Integration Requirements:**

- 5.6.6: Interactive input engine integrates seamlessly with the existing CLI command structure
- 5.6.7: Prompt interactions work correctly with the promptui adapter
- 5.6.8: Fuzzy finding operations integrate properly with the finder components
- 5.6.9: Template engine helpers function correctly within interactive workflows
- 5.6.10: No breaking changes to existing functionality

**Quality Requirements:**

- 5.6.11: All e2e tests pass consistently
- 5.6.12: Code coverage for interactive input components meets project standards (80%+)
- 5.6.13: Error handling is tested for user input validation, cancellation, and terminal issues
- 5.6.14: Tests run within reasonable time limits (< 30 seconds for full suite)
- 5.6.15: Test cleanup properly handles terminal state and mock inputs

### Dependency Injection Pattern

From `docs/architecture/components.md#dependency-injection`:

**Registration Pattern:**

```go
// Registry holds all component constructors
type Registry struct {
    promptPort     func() PromptPort
    finderPort     func() FinderPort
    templateEngine func() TemplateEngine
}

// Register interactive input components
func RegisterInteractiveComponents(reg *Registry) {
    reg.RegisterPromptPort(NewPromptUIAdapter)
    reg.RegisterFinderPort(NewFuzzyFinderAdapter)
    reg.RegisterTemplateEngine(NewTemplateEngine)
}
```

**Wiring in main.go:**

```go
func main() {
    // Build registry
    registry := registry.New()

    // Register interactive input components
    registry.RegisterPromptPort()
    registry.RegisterFinderPort()
    registry.RegisterTemplateEngine()

    // Build application container
    app := registry.Build()

    // Run application
    app.Run()
}
```

### SRP Decomposition for DI Container

**Extract These Helpers:**

1. **buildApplicationContainer(registry) *Application**
   - Single responsibility: Create fully wired application container
   - Calls all registration functions
   - Returns ready-to-run application
   - Why extract: Separation of container building from execution

2. **registerCommands(app *Application)**
   - Single responsibility: Register all CLI commands
   - Wires commands to container
   - Why extract: Command registration is distinct concern

3. **registerInteractiveComponents(registry)**
   - Single responsibility: Register all interactive input components
   - Calls individual registration functions
   - Why extract: Interactive component registration is cohesive task

**When to Decompose:**

- If main() exceeds 30 lines, extract buildApplicationContainer()
- If command registration is >10 lines, extract registerCommands()
- If interactive component registration is >10 lines, extract registerInteractiveComponents()

**Naming Standards:**

- Helpers: camelCase, verb-object pattern (buildApplicationContainer, registerCommands, registerInteractiveComponents)
- Registry methods: RegisterXxx pattern (RegisterPromptPort, RegisterFinderPort, RegisterTemplateEngine)

**Documentation Requirements:**

- Package comment explaining DI container and registry pattern
- GoDoc for buildApplicationContainer() explaining container construction
- GoDoc for each RegisterXxx() method explaining registration
- GoDoc for registry struct explaining dependency storage
- Inline comments for initialization order
