# Story 4.8: Epic 4 Architectural Refactoring - Go-First Approach

## Status: completed

## Story

As a developer,
I want to refactor Epic 4 components using Go idioms (concurrency, composition, simplicity) to eliminate god-objects and code duplication,
So that the codebase is performant, maintainable, and architecturally sound without over-engineering.

## Context

Epic 4 introduced schema-driven lookups and validation, but several architectural issues emerged:
- **God-objects:** Services with 8-10 attributes mixing multiple concerns
- **Code duplication:** Event publishing pattern repeated 18+ times
- **Event confusion:** Domain events mixed with application/telemetry events
- **Sequential I/O:** Missing opportunities for Go concurrency patterns
- **Leaky abstractions:** QueryService bypasses its own Router, holds redundant readers
- **Over-coupling:** Direct dependencies instead of standard ports

This refactoring focuses on **real architectural improvements** using Go's strengths:
- Goroutines and channels for concurrent I/O
- Composition and embedding over inheritance patterns
- Simple functions over complex object hierarchies
- Standard library patterns before custom abstractions

### 5. Cache Transactions: Concurrent Writes with Strategy Pattern

**Current Problem:** Sequential dual-writes to BoltDB + SQLite, inflexible two-phase commit

**Solution:** Concurrent writes using goroutines and channels with simple Strategy pattern for flexibility

**File:** `internal/app/persistence/transaction.go` (moved from vault/unit_of_work.go)

**Strategy Pattern (Simple):**
```go
// WriteStrategy defines how to execute write operations
type WriteStrategy interface {
    Execute(ctx context.Context, operations []WriteOperation, writers []spi.CacheWriterPort) error
}

// ParallelWriteStrategy executes writes concurrently
type ParallelWriteStrategy struct{}

// SequentialWriteStrategy executes writes sequentially (for testing/debugging)
type SequentialWriteStrategy struct{}

// CacheTransaction coordinates writes using a pluggable strategy
type CacheTransaction struct {
    writers   []spi.CacheWriterPort
    strategy  WriteStrategy
    operations []WriteOperation
    mu        sync.Mutex
}
```

**Changes:**
- Added simple Strategy interface (3 methods, minimal abstraction)
- ParallelWriteStrategy uses channels for concurrent BoltDB + SQLite writes
- Two-phase commit: BoltDB writes (parallel) → SQLite writes (parallel) → rollback on failure
- Flexible: Can swap strategies (parallel, sequential, custom)

**Performance Target:** 2-3x faster writes with ParallelWriteStrategy (measured via benchmarks)

**Impact:**
- Flexible storage coordination (add Redis, S3, etc. without changing transaction code)
- Reusable: Can be used by vault/, query/, or any cache writer
- Location: `app/persistence/` (application-level coordination, not domain pattern)

**Validation:**
- Benchmark shows ≥2x improvement on multi-note writes with ParallelWriteStrategy
- SequentialWriteStrategy available for debugging/testing
- All existing vault/indexer.go and vault/cache.go tests pass
- Transaction rollback tested with partial failures

### 6. QueryService: Concurrent Query Execution + Router Simplification

**Current Problem:**
- QueryService holds redundant `boltReader` + `sqliteReader` attributes (router already has them)
- Sequential query execution (hot path, then deep path on failure)
- Bypasses router for "optimization" in PathQuerySingle
- Observability (observer, failure trackers) embedded directly in QueryService

**Solution:**
- QueryService depends ONLY on router (remove direct reader dependencies)
- Concurrent queries: launch hot + deep queries in parallel, first success wins
- All queries go through router (no exceptions)
- **Move observability to telemetry events** (publish query performance events instead of observer)
- **Remove failure trackers** (use telemetry events for failure monitoring instead)

**Changes:**
```go
// Before: 10 attributes
type QueryService struct {
    mu sync.RWMutex
    boltReader   spi.CacheReaderPort        // ❌ Remove (router has this)
    sqliteReader spi.CacheReaderPort        // ❌ Remove (router has this)
    router       *StorageRouter             // ✅ Keep (only storage dependency)
    config       domain.Config
    log          zerolog.Logger
    eventBus     events.EventBus
    observer     *StalenessObserver         // ❌ Remove (use events instead)
    boltFailures   *BackendFailureTracker   // ❌ Remove (use events instead)
    sqliteFailures *BackendFailureTracker   // ❌ Remove (use events instead)
}

// After: 5 attributes
type QueryService struct {
    router   *StorageRouter  // Renamed from HybridStorageRouter
    config   domain.Config
    log      zerolog.Logger
    eventBus events.EventBus  // Keep for publishing telemetry events
    mu       sync.RWMutex
}
```

**Router Rename:**
- `HybridStorageRouter` → `StorageRouter` (simpler name, "Hybrid" is implementation detail)

**Observability via Events:**
- Publish `QueryPerformedEvent` with timing, result count, backend used
- Publish `QueryFailedEvent` for failures (replaces BackendFailureTracker)
- Subscribers can implement monitoring (Prometheus, logging, alerting)
- Decouples query logic from observability concerns

**Performance Target:** 2-3x faster queries when BoltDB has partial data (hot + deep run in parallel)

**Impact:**
- Attribute reduction: 10 → 5 (-50%)
- ~200 lines removed (observer, failure trackers eliminated)
- Proper encapsulation: router owns all routing decisions
- Observability via events (loosely coupled)

**Validation:**
- All queries use router (grep for direct reader access returns zero)
- Benchmark shows ≥2x improvement for queries requiring fallback
- No regression on hot-path-only queries
- Telemetry events published with correct timing and metadata

```go
// Interface for type-safe validators
type Validator[T domain.PropertySpec] interface {
    Validate(fieldName string, value any, spec T) error
}

// Registry with generics
type ValidatorRegistry struct {
    validators map[domain.PropertySpecType]any
}

func NewValidatorRegistry() *ValidatorRegistry

```

## Dev Notes

### Architectural Principles Applied

**Go Idioms Over Design Patterns:**
- Goroutines and channels for concurrency (not thread pools or executors)
- Simple functions for helpers (not wrapper classes)
- Composition via embedding (not inheritance hierarchies)
- Interfaces satisfied implicitly (not explicit base classes)
- **Minimal Strategy pattern where flexibility needed** (storage options in transactions)

**Domain vs Application Separation:**
- Domain: Entities, value objects, domain events (business concepts)
- Application: Services, workflows, telemetry, infrastructure coordination
- Patterns belong in application layer, not domain layer

**Simplicity Over Over-Engineering:**
- Helper functions preferred over classes (PublishAsync vs EventPublisher class)
- Direct solutions over pattern frameworks (channels with simple strategy vs complex UoW hierarchy)
- Standard library first (sync, context, channels)

**EventBus Attribute Kept Where Needed:**
- Services keep eventBus when they pass it to helper functions
- This is correct: helpers need bus parameter, services hold the dependency
- Not a god-object issue: eventBus is infrastructure, not business logic

### Performance Targets

**Concurrent Writes (CacheTransaction with ParallelWriteStrategy):**
- Baseline: Sequential writes (BoltDB then SQLite) ~100ms for 10 notes
- Target: Parallel writes with channels ~35-40ms for 10 notes (≥2x improvement)

**Concurrent Queries (QueryService):**
- Baseline: Sequential hot→deep fallback ~50ms when hot has partial data
- Target: Parallel hot+deep ~15-20ms (≥2x improvement)
- Hot-only path: No regression (should stay same or improve slightly)

### Why Services Keep EventBus

**FrontmatterService keeps eventBus:**
- Calls publishValidation(ctx, s.eventBus, s.log, ...) helper function
- Helper function needs bus to publish events
- Alternative would be dependency injection of publisher struct (over-engineering)

**TemplateEngine keeps eventBus:**
- Calls publishLookup(ctx, e.eventBus, e.log, ...) helper function
- Same rationale as FrontmatterService

**QueryService keeps eventBus:**
- Publishes telemetry events for query performance monitoring
- Replaces embedded observer and failure trackers with event-driven observability

### Why Observer and FailureTracker Removed from QueryService

**Problem:** Observability concerns embedded in QueryService
- observer.RecordStaleness() → tight coupling
- failureTracker.RecordFailure() → tight coupling
- Makes QueryService responsible for both querying AND monitoring

**Solution:** Event-driven observability
- Publish QueryPerformedEvent with timing, backend, result count
- Publish QueryFailedEvent for failures
- Monitoring services subscribe to events (loose coupling)
- QueryService focuses on queries, not monitoring infrastructure

**Impact:**
- QueryService simpler (no observer/tracker attributes)
- Observability extensible (add Prometheus, alerting via subscribers)
- Follows event-driven architecture pattern

### Technical Constraints

- Maintain hexagonal architecture (ports/adapters separation)
- Follow existing code standards from docs/architecture/coding-standards.md
- Preserve all existing API contracts (backward compatibility)
- Zero linting violations throughout refactoring
