# Story 4.4: Frontmatter End-to-End Validation

## Status

done

## Story

**As a** developer,
**I want** CommandOrchestrator.NewNote to perform complete frontmatter validation against schemas,
**so that** invalid notes are rejected before vault persistence and schema-driven constraints are enforced.

## Acceptance Criteria

**Frontmatter Validation Integration:**

- 4.4.1: CommandOrchestrator.NewNote includes comprehensive frontmatter validation using FrontmatterService.Validate()
- 4.4.2: Validation occurs after template rendering but before NoteID generation and persistence
- 4.4.3: Validation checks all schema constraints including FileSpec references, type validation, and required fields
- 4.4.4: Validation errors prevent note creation and return actionable error messages

**Schema-Driven Validation:**

- 4.4.5: FileSpec properties validate file existence via QueryService (FR8 query hints)
- 4.4.6: Schema validation enforces type constraints (string, number, bool, date, file)
- 4.4.7: Required field validation ensures all mandatory schema properties are present
- 4.4.8: Array validation checks both single values and arrays for array-required properties

**Error Handling and User Experience:**

- 4.4.9: Validation errors include field names, expected types, and remediation hints (FR5, FR7)
- 4.4.10: FileSpec errors suggest similar file names when exact matches fail
- 4.4.11: Validation failures abort the workflow before any persistence occurs
- 4.4.12: Error messages are user-friendly and actionable

**Testing:**

- 4.4.13: Unit tests cover validation success and failure scenarios in CommandOrchestrator
- 4.4.14: Integration tests verify end-to-end validation with real schemas and QueryService
- 4.4.15: Error message tests ensure remediation hints are accurate and helpful
- 4.4.16: All tests pass: `go test ./internal/app/command`

**Quality Gates:**

- 4.4.17: Linting passes: `golangci-lint run --fix internal/app/command`
- 4.4.18: Code coverage >90% for validation logic
- 4.4.19: Committed with message: `feat(command): add end-to-end frontmatter validation with schema constraints`

## Dev Notes

### Architecture Alignment (v0.6.8)

From `docs/architecture/components.md#commandorchestrator`:

The NewNote workflow must validate frontmatter against schemas before persistence. Validation includes:

- Schema constraint checking (required fields, types, ranges)
- FileSpec reference validation via QueryService
- Cross-field validation rules
- User-friendly error messages with remediation hints

### Error Handling Strategy

From `docs/architecture/error-handling-strategy.md`:

Validation errors should:
- Include field names and expected values
- Provide remediation guidance
- Be actionable for template authors
- Follow consistent error wrapping patterns

### Testing Strategy

From `docs/architecture/testing-strategy.md`:

- Unit tests for validation logic in CommandOrchestrator
- Integration tests for end-to-end validation with real schemas
- Error message testing for user experience validation
- Coverage requirements: >90% for validation code paths

### TDD Workflow

- RED: Write failing tests first (validation errors, success cases)
- GREEN: Implement minimal code to pass tests
- REFACTOR: Improve code quality while maintaining test passes

### Common Pitfalls

- Don't validate after persistence - validation must prevent invalid data
- Don't lose error context - always include field names and expected values
- Don't make errors too technical - focus on template author needs
- Don't skip FileSpec validation - this is core to schema-driven lookups
