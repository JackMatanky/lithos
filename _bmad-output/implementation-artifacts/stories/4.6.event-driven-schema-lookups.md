# Story 4.6: Event-Driven Schema Lookups

## Status

Done (Code Review: Fixed AC compliance issues)

## Story

**As a** developer,
**I want** schema-driven lookups to use the repository's event-driven architecture,
**so that** lookups are decoupled, observable, and support reactive behaviors.

## Context

This story integrates the established event-driven patterns from Epic 3 into Epic 4's schema-driven lookups. By publishing events for lookups, validations, and schema changes, the system becomes more observable and enables reactive features like cache invalidation and monitoring.

## Dev Notes

### Architecture Alignment (v0.6.8)

From `docs/architecture/components.md`:

The EventBus enables decoupling of components through domain events. Schema-driven lookups should publish events for observability and reactive behaviors, following the established patterns in the vault indexing system.

### Event Types

- **LookupPerformedEvent:** Tracks individual lookup operations
- **QueryPerformedEvent:** Tracks query operations with filters
- **SchemaLookupEvent:** Tracks schema resolution lookups
- **ValidationPerformedEvent:** Tracks validation outcomes
- **ValidationFailedEvent:** Tracks validation failures with remediation
- **NoteCreatedEvent:** Tracks successful note creation
- **SchemaUpdatedEvent:** Triggers reactive cache invalidation

### Testing Strategy

- Unit tests for event publishing in each service
- Integration tests for event-driven behaviors
- Event subscriber tests for reactive features
- Performance tests to ensure <5% overhead

### Common Pitfalls

- Events should be published asynchronously to avoid blocking operations
- Event publishing should not impact return values or error handling
- Subscribers should handle event processing failures gracefully
- Event payloads should include sufficient context for monitoring
