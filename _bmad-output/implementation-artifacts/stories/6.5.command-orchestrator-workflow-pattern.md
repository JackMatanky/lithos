# Story 6.5: CommandOrchestrator Workflow Pattern

## Status

ready-for-dev

## Story

**As a** developer,
**I want** CLI use cases extracted into explicit workflow objects,
**so that** the CommandOrchestrator becomes a lightweight coordinator and new commands are easy to add.

## Context

**Current Problem:**
CommandOrchestrator (CLIComander) is a 408-line service mixing:
- NewNote workflow (template rendering, validation, file creation)
- IndexVault workflow (delegation to VaultIndexer)
- Frontmatter parsing and validation
- Event publishing (NoteCreatedEvent)
- CLI command routing

Adding new commands requires modifying the orchestrator, violating Open-Closed Principle.

**Refactoring Goal:**
Extract use cases into workflow objects where:
1. Each CLI command has its own workflow
2. Workflows are injected via DI
3. CommandOrchestrator becomes pure routing
4. New workflows can be added without modifying orchestrator

**Target Architecture:**
```
CLIComander (100 lines) - Command routing only
├── NoteCreationWorkflow (100 lines) - NewNote use case
│   └── NoteEventPublisher (50 lines) - Event publishing
└── VaultIndexingWorkflow (50 lines) - IndexVault use case (delegates)
```

## Dev Notes

### Workflow Pattern Benefits

**Before:**
```go
// CLIComander has NewNote and IndexVault logic
// Hard to add new commands
```

**After:**
```go
// CLIComander routes to workflows
type Workflow interface {
    Execute(ctx context.Context, args Args) Result
}

// Easy to add new workflows
```

### Component Responsibilities

**NoteCreationWorkflow:** NewNote use case orchestration
**NoteEventPublisher:** Event publishing only
**VaultIndexingWorkflow:** IndexVault use case delegation
**CLIComander:** Command routing only

### Migration Path

1. Create NoteCreationWorkflow (most complex)
2. Create NoteEventPublisher
3. Create VaultIndexingWorkflow (simple)
4. Define Workflow interface
5. Refactor CLIComander to use workflows
