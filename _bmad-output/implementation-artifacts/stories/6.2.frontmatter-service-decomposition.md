# Story 6.2: FrontmatterService Decomposition - Separation of Concerns

## Status

ready-for-dev

## Story

**As a** developer,
**I want** FrontmatterService decomposed into focused validation components,
**so that** the 806-line service becomes maintainable and follows Single Responsibility Principle.

## Context

**Current Problem:**
FrontmatterService is an 806-line service handling:
- Schema validation (required fields, types, constraints)
- FileSpec validation (file references, wikilinks)
- Wikilink resolution and ambiguity checking
- Event publishing (ValidationPerformedEvent, ValidationFailedEvent)
- Remediation hint generation
- Type coercion and validation logic

This violates Single Responsibility Principle and makes testing and extending validation difficult.

**Refactoring Goal:**
Decompose into focused validators where each:
1. Handles one aspect of validation
2. Can be tested independently
3. Publishes its own events
4. Can be extended without affecting others

**Target Architecture:**
```
FrontmatterService (Core Orchestrator - 150 lines)
├── SchemaValidator (150 lines) - Schema compliance validation
├── FileSpecValidator (100 lines) - FileSpec property validation
│   └── WikilinkResolver (50 lines) - Wikilink resolution
├── ValidationEventPublisher (50 lines) - Event publishing
└── RemediationEngine (50 lines) - Error hint generation
```

## Dev Notes

### Component Responsibilities

**SchemaValidator:** Pure schema compliance (required fields, types, arrays)
**FileSpecValidator:** File reference validation
**WikilinkResolver:** Wikilink parsing and resolution
**ValidationEventPublisher:** Event publishing only
**RemediationEngine:** Error hint generation
**FrontmatterService:** Orchestration only

### Migration Path

1. Extract SchemaValidator first (most isolated)
2. Extract WikilinkResolver (no external dependencies)
3. Extract FileSpecValidator (uses WikilinkResolver)
4. Extract ValidationEventPublisher
5. Extract RemediationEngine
6. Refactor service to orchestrator
